# Менеджер проекта и команда AI-агентов

## Концепция

Заказчик взаимодействует **только с Менеджером проекта**. Аналитик, разработчик, тестировщик и документатор работают независимо и могут обмениваться адресованными рабочими сообщениями. Заказчик может посмотреть историю специалистов, но их сообщения не являются запросами пользователю.

Менеджер получает **компактное состояние задачи**: этап, версию требований, PR, завершённые результаты специалистов, открытые решения и последние существенные сообщения. Он не получает полное дерево исходников, все тест-кейсы и всю историю. У каждого специалиста собственные инструкции и соответствующий профессиональный контекст. Утверждённое ТЗ, GitHub PR SHA и QA-доказательства остаются общим источником истины.

Решения AI не имеют приоритета над условиями переходов на backend. Temporal сохраняет выполнение и исключает параллельную работу над одной задачей.

## Реализация

- **PostgreSQL:** `manager_messages` (сохранённая переписка, статус обработки сообщения, источник ответа) и `manager_requests` (типы требуемых решений, состояние, источник, субъект согласования).
- **Temporal:** `projectManagerReply` запускает `resolvePeerQuestions` и `completeManagerMessage`. Вызов менеджера происходит при сообщении заказчика; вопросы специалистов также обрабатываются на контрольных точках рабочего workflow.
- **Codex CLI:** для менеджера используется существующее подключение подписки ChatGPT; контекст создаётся из краткого состояния и изолирован от рабочих файлов разработчика. Специализированные агенты не заменены одной большой моделью.
- **REST:** `GET /api/projects/:id/tasks/:taskId/manager` предоставляет состояние, `POST .../manager/messages` принимает сообщение и сохраняет его до вызова AI; `POST .../manager/messages/:messageId/retry` повторяет ошибочную обработку. `POST .../manager/requests/:requestId/decision` применяет явное решение с повторной серверной проверкой. `POST .../manager/continue` — восстановление или повторный запуск при имеющейся ветке/PR.
- **UI:** отдельный чат с Менеджером проекта, сообщения заказчика справа, менеджера слева; внутренние сообщения специалистов — сворачиваемая история. Решения и восстановление доступны в компактной полоске под чатом.

## Согласование ограниченных визуальных проверок

Если инструментов реального браузерного тестирования нет, изучение исходного кода **не равно** визуальной проверке. QA-отчёт отмечает такие кейсы как `blocked` или `not_run`, с обоснованием `tool_unavailable`, `environment_unavailable` или `manual_only`.

При достоверно завершённом QA с достаточными доказательствами Менеджер спрашивает заказчика:

1. **Разрешить слияние с непроверенными сценариями.** Вызов существующего QA waiver проверяет текущую версию ТЗ, список кейсов, отсутствие подтверждённых дефектов, commit SHA PR и полномочия пользователя. Исключения записываются в `qa_merge_waivers`. GitHub CI и ограничения ветки не обходятся.
2. **Ждать появления инструментов.** Состояние `waiting` остаётся в БД, код и PR сохраняются, задача остаётся в тестировании. При появлении средств можно повторить тестирование, а решение о риске впоследствии пересмотреть.

При настоящих дефектах менеджер не может разрешить пропуск проверок: задача должна вернуться разработчику.

## Восстановление незавершённой задачи

Для ранее зависшей задачи (например, размещение фигур по окружности) команда «Продолжить / восстановить работу» проверяет **существующий PR в GitHub**, а не просит заказчика отправлять diff. Если аналитик задал технический вопрос о diff/PR и уже доступный PR подтверждён, этот вопрос закрывается как внутренний — но не считается прохождением тестов.

Если предыдущее заключение аналитика — неопределённость из-за отсутствующего diff, оно переводится в повторную проверку с актуальными доказательствами. Если имеется реальное изменение бизнес-требований, оно **не** согласовывается автоматически.

На этапе `testing` система использует существующую ветку и PR и проходит повторную сверку аналитиком и QA. На этапе `development` использует существующий механизм продолжения разработки. Если Temporal/Codex уже выполняет задачу, второй процесс не запускается.

## Как агенту передаётся сообщение

Каждый вызов получает рамку роли, правила проекта, фрагменты утверждённого ТЗ, соответствующие этапу документы и релевантную историю. Внутренние заметки трактуются как ненадёжная рабочая информация, а не как самостоятельные разрешения на изменение требований.

Результаты специалистов сохраняются отдельно от текстовых сообщений. Менеджер рассказывает заказчику о них, но **не может самовольно изменить результат QA**, PR SHA или допустимый статус. Решения об изменениях требований и непроверенных сценариях проходят существующие проверяемые серверные операции.

## Оставшиеся ограничения

- Изолированный Test Runner с Playwright/Chromium, развёртыванием приложения, скриншотами и трассировкой пока отсутствует. Менеджер должен честно сообщать об этом.
- Сквозное испытание **реальной** старой задачи через подключённые PostgreSQL, Temporal, Codex и GitHub нельзя заменить модульными тестами и CI.
- Менеджер получает события от backend и специалистов, но не выполняет непрерывный платный AI-опрос. Детерминированные переходы выполняются Temporal и сервером.
- Фактическое согласование QA выполняется только после проверки необходимых доказательств и полномочий, даже если модель или пользователь в свободном тексте заявляют «разрешаю».
