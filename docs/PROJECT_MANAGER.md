# Менеджер проекта и команда AI-агентов

## Концепция

Менеджер проекта координирует поручения и отвечает за отчёт о состоянии проекта. Аналитик задаёт вопросы по требованиям в карточке задачи от своего имени. Карточка хранит рабочие сообщения, ответы и решения, которые используют участники процесса.

Менеджер получает **компактное состояние задачи**: этап, версию требований, PR, завершённые результаты специалистов, открытые решения и последние существенные сообщения. Он не получает полное дерево исходников, все тест-кейсы и всю историю. У каждого специалиста собственные инструкции и соответствующий профессиональный контекст. Утверждённое ТЗ, GitHub PR SHA и QA-доказательства остаются общим источником истины.

Решения AI не имеют приоритета над условиями переходов на backend. Temporal сохраняет выполнение и исключает параллельную работу над одной задачей.

## Реализация

- **Проектный чат.** `POST /api/projects/:id/manager/inbox` сохраняет сообщение в PostgreSQL и возвращает `202`, независимо от доступности Temporal. Обычный диалог не создаёт запись `project_pm_orders`.
- **Поручения.** После подтверждённой изменяющей операции или запуска фонового процесса backend создаёт `project_pm_orders` и связывает с исходным сообщением; чтение данных и служебные события не создают поручений. Ответ владельца возобновляет существующее `waiting_user`. Если Codex успел выполнить действие и завершился с ошибкой, поручение восстанавливается по журналу инструментов.
- **Сессии.** У ПМ нет постоянно работающего Codex-сеанса. Сообщение выполняется временным запуском, фоновые процессы отслеживаются через Temporal.
- **Повторная отправка.** Клиент создаёт `requestId` на сообщение. Повтор с тем же ключом и содержимым возвращает исходные идентификаторы сообщения и поручения (если оно создано). Повтор с изменённым содержимым получает `409`. Ключ действует в пределах пользователя и проекта.
- **Доставка.** Диспетчер передаёт сохранённый ход в `processProjectManagerInbox` и отмечает доставку после подтверждения Temporal. При недоступности Temporal он повторяет запрос с тем же workflow ID. После перезапуска диспетчер подхватывает ожидающие записи. Завершение делегированной работы также сохраняет следующий ход ПМ в этой очереди.
- **Вопросы владельцу.** Вопросы аналитика и предложения изменить требования остаются в карточке задачи с указанием автора. После ответа на последний открытый вопрос анализ возвращается в очередь. В общем чате ПМ показывает статус и ссылку на задачу. Собственную тему ПМ открывает вместе с первым сообщением и закрывает после разрешения поручения.
- **Очередь разработки.** ПМ читает причины ожидания из той же очереди, что и Центр процессов. Подтверждённый запуск подхватывается после анализа, если утверждённая ревизия и объём работы актуальны.
- **Повтор обработки.** Когда выполнение окончательно завершилось ошибкой, `POST .../manager/inbox/:messageId/retry` повторно ставит то же сообщение в очередь с новым идентификатором попытки Temporal. Эта операция отличается от повтора отправки при неизвестном результате HTTP-запроса.
- **Чат задачи.** `manager_messages` и `manager_requests` хранят переписку задачи и запросы решений. Маршруты под `/api/projects/:id/tasks/:taskId/manager` используют отдельный workflow `projectManagerReply`. Он разрешает внутренние вопросы, применяет подтверждённые решения и продолжает работу по существующему PR.
- **Codex CLI.** ПМ использует подключённую подписку ChatGPT и краткий контекст проекта и поручения.

## Согласование ограниченных визуальных проверок

Если инструментов реального браузерного тестирования нет, изучение исходного кода **не равно** визуальной проверке. QA-отчёт отмечает такие кейсы как `blocked` или `not_run`, с обоснованием `tool_unavailable`, `environment_unavailable` или `manual_only`.

При достоверно завершённом QA с достаточными доказательствами Менеджер спрашивает заказчика:

1. **Разрешить слияние с непроверенными сценариями.** Вызов существующего QA waiver проверяет текущую версию ТЗ, список кейсов, отсутствие подтверждённых дефектов, commit SHA PR и полномочия пользователя. Исключения записываются в `qa_merge_waivers`. GitHub CI и ограничения ветки не обходятся.
2. **Ждать появления инструментов.** Состояние `waiting` остаётся в БД, код и PR сохраняются, задача остаётся в тестировании. При появлении средств можно повторить тестирование, а решение о риске впоследствии пересмотреть.

При настоящих дефектах менеджер не может разрешить пропуск проверок: задача должна вернуться разработчику.

## Восстановление незавершённой задачи

При сообщении заказчика Менеджер сначала обрабатывает внутренние вопросы. Если задача на разработке или тестировании, свободна и не ожидает решения заказчика, Temporal запускает подходящий следующий этап. Менеджер сообщает результат запуска. При активном процессе повторный исполнитель не нужен. Ранее отклонённое изменение требований возвращается разработчику по действующему ТЗ.

Для ранее зависшей задачи (например, размещение фигур по окружности) команда «Продолжить / восстановить работу» проверяет **существующий PR в GitHub**, а не просит заказчика отправлять diff. Если аналитик задал технический вопрос о diff/PR и уже доступный PR подтверждён, этот вопрос закрывается как внутренний — но не считается прохождением тестов.

Если предыдущее заключение аналитика — неопределённость из-за отсутствующего diff, оно переводится в повторную проверку с актуальными доказательствами. Если имеется реальное изменение бизнес-требований, оно **не** согласовывается автоматически.

При наличии открытого PR на ветке задачи и отсутствии замечаний к реализации система запускает сверку аналитиком и QA, даже если карточка осталась в разработке. При замечаниях или отсутствии готового PR действует существующий механизм продолжения разработки. Если Temporal/Codex уже выполняет задачу, второй процесс не запускается.

## Как агенту передаётся сообщение

Каждый вызов получает рамку роли, правила проекта, фрагменты утверждённого ТЗ, соответствующие этапу документы и релевантную историю. Внутренние заметки трактуются как ненадёжная рабочая информация, а не как самостоятельные разрешения на изменение требований.

Результаты специалистов сохраняются отдельно от текстовых сообщений. Менеджер рассказывает заказчику о них, но **не может самовольно изменить результат QA**, PR SHA или допустимый статус. Решения об изменениях требований и непроверенных сценариях проходят существующие проверяемые серверные операции.

## Оставшиеся ограничения

- Изолированный Chromium/Playwright и проверяемые скриншоты с SHA исходников доступны для задач и целей ПМ. Для проверки опубликованного production-окружения всё ещё нужно удостовериться в доступе к нему и фактически развёрнутом SHA; локальную проверку нельзя считать подтверждением production.
- Сквозное испытание **реальной** старой задачи через подключённые PostgreSQL, Temporal, Codex и GitHub нельзя заменить модульными тестами и CI.
- Менеджер получает события от backend и специалистов, но не выполняет непрерывный платный AI-опрос. Детерминированные переходы выполняются Temporal и сервером.
- Фактическое согласование QA выполняется только после проверки необходимых доказательств и полномочий, даже если модель или пользователь в свободном тексте заявляют «разрешаю».
