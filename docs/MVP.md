# MVP — реализация и границы

Обновлено: 9 ноября 2026 года.

## Цель

AI Development Orchestrator управляет задачами совместной разработки человека и AI: от анализа требований до проверенного PR, обновления документации и завершения задачи.

## Реализовано в репозитории

- Проекты, базовая авторизация и доступы, Kanban и список задач, карточки, чат с AI.
- Правила проекта, вложенные страницы документации, импорт Markdown из GitHub, статусы реализации, история некоторых обновлений.
- GitHub-подключение, отдельные ветки, PR, проверка GitHub Check Runs и слияние.
- Codex CLI через подписку ChatGPT с отдельным исполнительным контейнером.
- Temporal: разработка, отдельный AI-тестировщик, возвраты при ошибках и повторные попытки.
- Центр процессов для наблюдения за исполнением и ошибками.
- Настройки имени и инструкций агента для этапов workflow.
- **QA-каталог:** пользовательские сценарии, тест-кейсы, результаты AI/ручных проверок и история редактирования кейсов.
- **Автоматический test design:** QA-агент создаёт или актуализирует тестовую документацию непосредственно перед тестированием, после сверки PR с актуальным ТЗ.
- **Проверка PR:** AI-тестировщик получает подготовленный план, фиксирует результат каждого кейса. При слиянии задач с QA-планом требуется успешно протестированный SHA.

## Целевой путь

Создание задачи → Анализ → Разработка → *Сверка требований аналитиком* → *QA test design* → Тестирование → Ожидает слияния → Документация → Готово.

*Сверка требований* и *QA test design* — подэтапы Temporal, не отдельные колонки Kanban.

## Изменения требований

Система сохраняет историю версий ТЗ. После разработки аналитик сверяет PR с утверждённым поведением; существенные отклонения требуют подтверждения пользователя. Ручное изменение текста задачи на любом этапе запускает проверку аналитика. QA-план и результат тестов связываются с версией ТЗ.

## Что пока не является готовой возможностью

- Подключение реального браузерного E2E Test Runner (например, Playwright), развёртывание изолированных тестовых окружений, автоматическое получение UI-артефактов.
- Полноценная матрица покрытия, глобальный impact analysis, регрессия на уровне всей кодовой базы и автоматическое сопоставление кейсов с компонентами.
- Восстановление активной команды Codex после перезапуска исполнителя.
- Production-hardening Temporal, секретов, разграничения доступа и наблюдаемости.
- Продвинутые роли, приглашения пользователей, полный граф зависимостей и управление релизами.
- Полная матрица покрытия и согласование изменений ожидаемых результатов между версиями тест-кейсов.

## Недоступные проверки и ручное решение

QA-агент пытается выполнить все доступные проверки. Когда инструмент или среда отсутствует, он сообщает причину и непроверенные сценарии. Администратор может согласовать исключение именно этих сценариев с записью причины, списка и SHA PR. Слияние не происходит автоматически: GitHub CI и правила ветки остаются обязательными. При ошибках тестов, дефектах или отсутствии доказательств возможность исключения недоступна.

## Правило качества

Успешная сборка TypeScript не означает, что пользовательские сценарии успешно пройдены. AI-тестировщик обязан ссылаться на реальные результаты; непроверенные сценарии помечаются как заблокированные или не выполненные.



## Передача рабочих комментариев и безопасная отмена

Аналитик, разработчик и тестировщик могут оставлять друг другу сообщения с конкретным адресатом и источником. Вопросы до ответа блокируют процесс. В интерфейсе задачи действия показываются в закреплённой полоске, а весь ход работ — в единой правой переписке, без цветового кодирования каждого сообщения.

Отмена до слияния закрывает PR и удаляет ветку UUID задачи (не удаляя запись PR из GitHub); данные удаляются только при доказанной принадлежности отменяемой задаче. Если ветка используется другой задачей, есть незавершённый процесс, слитый PR или связанные документы, операция запрещается до разрешения зависимостей.

Подробности: [Рабочие сообщения и контрольные точки](TASK_COLLABORATION.md).


## Единая точка общения с пользователем

В задачах заказчик видит чат **Менеджера проекта** и компактные действия для него: ответ на уточнения, согласование изменения ТЗ, решение о выпуске без отдельных визуальных тестов или ожидании инструментов, восстановление зависшей разработки/QA. Внутренняя переписка между специалистами доступна для просмотра, но без необходимости непосредственно отвечать исполнителям. Системные ограничения и QA-проверки остаются на backend и Temporal.
