# DevOps и выкладка

## Жизненный цикл

Анализ → Разработка → Тестирование → Слияние PR → **Выкладка (необязательный этап)** → Документация → Готово.

DevOps — сквозная роль, способная сопровождать CI и работу окружений независимо от этапа задачи. Отдельный этап «Выкладка» отражает доставку уже слитого кода, а не повторную разработку.

## Текущий режим

У проекта есть `project_deployment_settings.mode`:
- `skip` (по умолчанию) — после подтверждённого GitHub merge задача сразу переходит к документации, при этом сохраняется `task_deployment_records.status=skipped` и событие с объяснением. Это **не** означает, что приложение развернуто.
- `manual` — после GitHub merge задача переходит в `deployment`. Пользователь может зафиксировать ручное подтверждение с доказательствами либо явно пропустить выкладку с причиной. В обоих случаях задача передаётся документации; записи остаются в истории.

Для перехода в `done` по-прежнему требуется обновление документации. Режим выкладки устанавливается в настройках Workflow. Настройка применяется к **следующим слияниям** и не переписывает историю уже обработанных задач. Консультационный `@DevOps` не выполняет deploy.

## Следующее расширение: самостоятельная настройка GitHub CI/CD

Развертывание через GitHub Actions должно стать полноценным действием DevOps-агента через специализированный API, а не произвольным shell-доступом.

1. DevOps читает подключенный GitHub-репозиторий, существующие Actions, структуры сборки, Docker и описания сред. Анализирует текущие CI jobs, результаты и длительности. Сопоставляет с требованиями развёртывания.
2. Для нового окружения собирает минимальные недостающие данные (тип платформы, адрес/регион, учётные данные, необходимые разрешения, healthcheck). Секреты вводятся пользователем через защищённые подключения или GitHub Secrets. Модель не получает секреты и не печатает их в логах.
3. Создаёт отдельную ветку и PR для `.github/workflows/*`, deployment scripts, конфигурации и эксплуатационной документации. Проверяет YAML/сборку/тесты и применяет настройки только после успешных проверок и разрешённого merge.
4. Создаёт конфигурацию среды с `environment_id`, GitHub `environment`, целевой веткой, правилами approvals, `concurrency`, healthcheck, rollback и допустимым уровнем доступа. Самостоятельно управляет **несекретной** конфигурацией в пределах прав проекта.
5. Исполняет выкатку через Temporal: `prepare -> validate SHA / approvals -> dispatch workflow -> observe run and jobs -> verify health -> confirm release`. Каждая операция снабжается idempotency key, SHA и correlation ID; один релиз для нескольких задач поддерживается.
6. При ошибке — диагностирует первопричину, повторяет только нестабильный неуспешный шаг либо откатывает до последнего проверенного релиза. Подробности, статусы и результаты доступны в Центре процессов.
7. Не заменяет функциональный QA и не отключает обязательные проверки, не запускает параллельные выкладки в одну среду; повторные сборки отменяются или используются готовые артефакты, когда это безопасно.

Будущий режим `github_actions` разрешается включить **только после** проверки готовности среды и работающего адаптера GitHub Actions. Не добавлять такой режим как фиктивный toggle, который допускает задачу в «Готово» без доставки.

### Роли и границы

- Developer: приложение и исправления продукта.
- QA: подтверждение функциональной корректности.
- GitHub Integrator: слияние проверенного PR в правильный base.
- DevOps: конфигурация CI, оптимизация Actions и доставка проверенного SHA, инфраструктурная диагностика и безопасный откат.
- Technical Writer: документация фактически изменённого поведения и эксплуатационной конфигурации.

**Инвариант:** `skipped` и `manual_confirmed` различаются от машинно подтвержденного `deployed`. Пропуск этапа не должен отображаться как успешная выкладка.
