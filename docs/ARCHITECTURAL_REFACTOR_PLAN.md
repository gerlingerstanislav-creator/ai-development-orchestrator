Есть рабочие выделенные модули и тесты; рефакторинг должен **опираться** на них, а не создавать вторую реализацию.
Проверенные `main` workflow CI до начала работ завершились успешно. Это исходный baseline, а не подтверждение будущих изменений.

### Особые риски

- `dbInit()` содержит не только создание/изменение схемы, но и изменение данных при запуске (в частности, сброс `projects.agents_running`). Переносить SQL в «миграции» без классификации DDL, одноразовых backfill и runtime-политик нельзя.
- Изменение порядка вызова Activities, имён workflow и детерминированного кода Temporal может повредить уже запущенные процессы.
- HTTP-коды 404/409/5xx из Runner по-разному интерпретируются механизмом восстановления. Нельзя нормализовать их до одной общей ошибки.
- Сценарии PM, QA и агента могут параллельно менять задачу; блокировки, идемпотентность и принадлежность проекту требуют интеграционных тестов.
- Полное форматирование файлов затруднит ревью и поиск функциональных изменений.

## Целевые границы модульного монолита

`apps/api/src/modules/<domain>/`: `projects`, `tasks`, `workflow`, `agents`, `execution`, `quality`, `knowledge`, `planning`, `integrations`, `deployment`.

- **domain**: чистые правила и инварианты, без Fastify, PostgreSQL или Temporal;
- **application**: сценарии использования и транзакционные границы;
- **infrastructure**: PostgreSQL, Runner/GitHub-адаптеры и сериализация;
- **api**: HTTP DTO, проверка внешнего ввода, авторизация, ответы.

Слои создаются там, где имеются реальные зависимости и сложность, а не механически для каждого файла. Композиция предпочтительнее наследования. `apps/api/src/infrastructure/runner-http-client.ts` — первый безопасный шаг: транспорт вынесен из Temporal Activities, правила восстановления остались на месте.

### Границы ответственности системы

- Temporal: долгоживущий процесс, ожидание, retry и история; Activities: внешние эффекты и делегирование приложениям.
- Оркестратор: права, задачи, инструменты, хранилище, обязательные проверки и маршрутизация; агент: выбор способа достижения ожидаемого результата.
- Межагентные сообщения: только через задачи, сообщения и предусмотренные инструменты. Никакой скрытой «фоновой» переписки.
- Runner: очереди/задания, Codex-процесс, изоляция, Git/PR, QA, доказательства и журнал — отдельные компоненты с сохранением существующих HTTP-контрактов.
- Web: функциональные модули с общим типизированным API-клиентом, без изменения визуальной композиции.

## Порядок безопасной миграции

1. **Базовые контракты и тесты.** Инвентаризация внешних API и Runner/Temporal-контрактов; фиксация поведения тестами. Вынести общие транспортные адаптеры, типы ошибок и DTO с проверкой на внешних границах. Не менять recovery-политику.
2. **Схема PostgreSQL.** Отделить startup от схемы. Классифицировать SQL по видам: DDL, одноразовые backfill, runtime-сбросы. Добавить упорядоченные миграции, блокировку одновременного запуска и baseline для существующей БД; проверить новую и обновляемую установки на копиях данных.
3. **Backend.** Переносить маршруты небольшими доменными срезами с собственным репозиторием и use case, сохраняя URL, payload, ACL и транзакции. Для каждого среза удалить старый путь, не оставлять дубли.
4. **Temporal.** Разделить определения процессов, Activities, сервисы и внешние адаптеры. Перед изменением существующих workflow проверить историю/идентификаторы; использовать версионирование при несовместимых изменениях.
5. **Codex Runner.** Поочерёдно выделить жизненный цикл задания, процесс Codex, workspace, Git/PR, QA, evidence, limits. Покрыть 404/409, interrupt/resume, cancel, retry, concurrency и принадлежность задаче.
6. **Frontend.** Сначала API-клиент/авторизация, затем layout, задачи/Kanban, workflow, PM-чат, процессы, документация, QA, команда и настройки; проверять визуальные сценарии по шагам.
7. **Регрессия и документация.** TypeScript, сборки, тесты модулей, интеграционные сценарии с PostgreSQL/Temporal, E2E в доступной среде, сборки Docker, совместимость API/MCP и ручные сценарии, где нет автоматизации.

## Условия каждого PR

- Начинать от свежего `main`; один ограниченный архитектурный срез на PR.
- Сначала тест-контракт поведения, затем перенос; отсутствие изменения публичного поведения проверяется отдельно.
- CI (и необходимые интеграционные проверки) действительно выполнены; результат недоступной проверки — `not run`, не `passed`.
- Для миграций и Temporal требуется отдельное обоснование обратной совместимости и механизм rollback.
- Не сливать PR с неизвестным статусом проверок; после merge следующий этап начинать от нового `main`.
- В отчёте указывать выполненное, не выполненное и оставшийся риск. Рефакторинг завершён лишь после всех архитектурных критериев, а не после уменьшения размеров файлов.
