# Документация проекта: миграция и безопасный откат приложения

## Изменения в схеме и совместимость

Миграция `initDocumentationSystem` при запуске API добавляет пять неизменяемых
системных корней для каждого проекта, переносит существующие корневые страницы
под подходящий раздел и оставляет неоднозначные страницы под «Исходными
материалами и исследованиями». Идентификаторы страниц, вложенные страницы,
`import_source`, тексты и ссылки не пересоздаются. Повтор миграции безопасен.

Для импорта используются таблицы `document_import_jobs`,
`document_import_fragments`, `document_import_topics`,
`document_import_proposals`, `documentation_questions` и исторические
`document_import_checkpoints`. Данные сохраняются в томе PostgreSQL `db_data`.
Temporal хранит историю исполнения в отдельном томе `temporal_data`.

**Важное ограничение:** старые версии API, которые создают страницы
`parent_id=NULL`, несовместимы с защитой корней. Если требуется возврат
к старому интерфейсу или поведению, используйте совместимую сборку с
поддержкой пяти системных корней. Не отключайте DB-триггер, чтобы
«починить» старый путь создания документа.

## До релиза

1. Зафиксируйте проверенный SHA текущей версии и теги Docker-образов;
   убедитесь, что их можно повторно развернуть.
2. Дождитесь завершения активных импортов или остановите
   `temporal-worker`, сохранив Temporal и PostgreSQL работающими.
   Зафиксируйте UUID активных `document_import_jobs`.
3. Сделайте проверенную резервную копию PostgreSQL **и** резервную копию
   тома `temporal_data`, если нужен полный disaster recovery.

Пример сохранения SQL-резервной копии с хоста Docker Compose:

```bash
docker compose exec -T db pg_dump -U orchestrator -d orchestrator -Fc > ado-before-docs-upgrade.dump
pg_restore --list ado-before-docs-upgrade.dump > /dev/null
```

Это не заменяет тестовое восстановление копии в отдельную БД.

## Откат версии приложения без отката данных

1. Остановите новые запуски импорта и зафиксируйте состояния
   `document_import_jobs` и UUID уже сохранённых страниц.
2. Разверните **заранее проверенные, совместимые с новой схемой**
   Docker-образы `api`, `web` и `temporal-worker`, сохранив
   тома `db_data`, `temporal_data` и `codex_auth`.
3. Не выполняйте `docker compose down -v`, `DROP TABLE`,
   `TRUNCATE`, `pg_restore --clean` или обратную миграцию данных.
   Обычный откат кода не должен стирать созданные после релиза страницы.
4. Проверьте `/api/health`, чтение документации, доступность
   «Вопросов к ПО», ручную правку страницы и контрольные точки импорта.
5. Возобновите незавершённые импорты в Центре процессов по **их старым
   job ID** после запуска совместимого worker. Новый процесс по тому же
   материалу создавать не требуется.

Если доступен только **старый несовместимый** API, допустим временный
режим чтения страниц и исполнения остальных процессов. Создание корневых
документов и старый импорт необходимо заблокировать до развёртывания
совместимого hotfix. Откат схемы ради старой версии не допускается.

## SQL-проверки после развёртывания / отката

```sql
-- Для каждого проекта должно существовать ровно пять системных корней.
SELECT project_id, count(*) AS root_count
FROM documents
WHERE system_key IS NOT NULL AND parent_id IS NULL
GROUP BY project_id;

-- Выявить потерянные связи или ошибочные корни (ожидается 0 строк).
SELECT d.id, d.project_id, d.title, d.parent_id
FROM documents d
WHERE d.system_key IS NULL AND d.parent_id IS NULL;

-- Контрольные точки и страницы сохраняются при откате версии кода.
SELECT job_id, topic_key, status, cursor, page_id
FROM document_import_topics
ORDER BY job_id, topic_key;

SELECT id, project_id, import_source, updated_at
FROM documents
WHERE import_source LIKE 'topic:%'
ORDER BY project_id, import_source;
```

## Восстановление при повреждении БД

Полный restore — **аварийная операция**, не стандартный rollback релиза:
он потеряет новые документы и контрольные точки, записанные после бэкапа.
Сначала сохраните отдельно все новые записи и журнал процессов,
проверьте тестовое восстановление в изолированной БД и только затем
планируйте возврат данных. При наличии сохранных данных предпочтителен
`forward fix` схемы/кода без разрушительной обратной миграции.

## Регрессионные проверки

`documentation-system.test.mjs` проверяет новое/старое дерево и повтор
миграции; `project-analyst.test.mjs` — ответ ПО и возобновление того же
импорта; `coffee-preorder-pilot.test.mjs` читает зафиксированный
снимок всех девяти исходников Coffee Preorder и проверяет прерывание,
частичные страницы, межфайловую тему и защиту ручного текста.
Тесты с подменённым Codex **не доказывают качество реального AI-анализа**:
проверку формулировок ТЗ и границ MVP нужно проводить отдельно в
развёрнутой системе с подключённой подпиской Codex.
