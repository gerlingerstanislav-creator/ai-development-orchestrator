# Собственный CI/CD, архитектурное ревью и команда агентов

## Назначение

AI Development Orchestrator выполняет технические проверки и независимое архитектурное ревью через собственный Codex Runner. GitHub используется для хранения веток, PR и отображения commit status, а не для исполнения проверок. **GitHub Actions для CI не требуются.**

## Роли

- **PM** — координация, подтверждения владельца, переотправка задач.
- **Аналитик BA/SA** — бизнес-цели, требования, API, данные, сценарии и критерии приёмки. Работающий этап `analysis` остаётся единым и хранит предыдущие результаты. Пользовательские инструкции прежнего BA сохраняются для консультаций.
- **Архитектор (Tech Lead)** — консультации по техническим решениям и обязательное независимое ревью реального PR по SHA. Обращение из чата: `@Architect`. Проверяет совместимость API и БД, миграции, безопасность и регрессии; рекомендации, не являющиеся блокирующими, не препятствуют слиянию.
- **Разработчик** — реализация и исправление находок ревью и QA, включая разрешение merge conflicts, в той же ветке/PR.
- **QA** — функциональные сценарии, реальные браузерные проверки Chromium/Playwright, регрессия.
- **DevOps** — собственный CI/CD, окружение, автоматическая выкладка.
- **Документатор** — обновление проверенной реализации после слияния.

## Жизненный цикл PR

1. Разработчик обновляет ветку задачи и PR.
2. Temporal запускает технический CI в изолированном Codex Runner для конкретного head SHA и base SHA: совместимость с base, доступные проверки сборки и типов, программные тесты. Результаты (выходные коды, логи) сохраняются в `quality_gate_runs` и `process_events`.
3. Архитектор независимо читает код и diff, возвращает структурированное ревью `approved` либо `changes_requested`; результат привязан к тому же commit SHA. При блокирующих замечаниях задача возвращается разработчику с описанием недостатков.
4. QA выполняет тесты на конкретном SHA; при дефектах возвращает разработчику.
5. MergeService требует одновременно актуального успешного собственного CI, ревью архитектора, QA-отчёта и отсутствия неразрешённых конфликтов. Смена head SHA или base SHA обнуляет применимость предыдущих результатов: проверки нужно повторить.
6. При успешном merge фиксируется SHA; автоматическая выкладка выполняется только при настроенном окружении, иначе этап помечается ручным или пропущенным согласно настройкам проекта.

Результаты можно посмотреть в `GET /api/projects/:id/tasks/:taskId/quality-gates`. Администратор может повторно запросить проверки через `POST` по тому же URL. Все действия отслеживаются через Temporal и события процессов. Статусы публикуются в GitHub как `ado/self-hosted-ci` и `ado/architecture-review`; токен подключения должен иметь разрешение **Commit statuses: Read and write**. Если GitHub отказывает в записи статуса, это фиксируется как предупреждение, а локальный отчёт сохраняется.

Для проектов без достаточной среды отдельные проверки могут завершиться ошибкой/blocked. **Отсутствующая проверка не должна считаться пройденной**. Требования к системным зависимостям проекта (например, тестовая БД) нужно обеспечить изолированно, не используя продакшен-данные или секреты. Независимый QA дополняет технический CI.

## Автоматическая выкладка без Actions

Настроить в разделе проекта «Workflow → Выкладка → Автоматически через SSH и Temporal»:

- HTTPS URL для последующего healthcheck.
- SSH-хост, пользователя и абсолютный путь с кодом на сервере.
- Отдельный приватный SSH-ключ с минимальными правами и подтверждённый fingerprint host key в формате OpenSSH `known_hosts`.

Приватный ключ сохраняется зашифрованным в `project_deployment_ssh`, доступ к конфигурации имеет только администратор проекта. Перед выкладкой Temporal проверяет, что SHA является предком основной ветки, затем подключается по SSH с `StrictHostKeyChecking=yes`, обновляет точный SHA и выполняет `docker compose up -d --build`, после чего трижды проверяет HTTPS. Состояние сохраняется в `deployment_runs` и `task_deployment_records`. Повторная выкладка в одну среду блокируется действующей уникальностью активного процесса.

GitHub Secrets невозможно получить обратно через API, поэтому существующие секреты старого Actions-workflow нужно **ввести в защищённые настройки приложения заново**. Пока SSH-настройки не заполнены, автоматическая выкладка не начнётся; не следует объявлять приложение развёрнутым.

## Принципы безопасности

- Runner выполняет проверки кода в изолированной песочнице Codex, не монтируя Docker socket.
- Архитектор проводит ревью **без записи в исходники**; разработчик отвечает за исправления.
- Права GitHub и SSH-учётных данных ограничены назначением. Технические проверки привязаны к SHA, не к названию ветки.
- Нельзя ослаблять безопасность ветки или объявлять skipped/blocked успешной проверкой.
- После переноса CI не создавать новые GitHub Actions workflow для автоматического запуска без явного решения владельца.
