# Универсальные поручения агентам (v13)

## Цель

ПМ и участники команды могут делегировать конкретный результат подходящему специалисту без маршрутизации по ключевым словам и без фиктивных изменений кода. Это отдельная модель исполнения, а не второй Kanban.

## Контракты

- `agents.capabilities(role)` — запрашивает реально разрешённые инструменты и ответственность роли.
- `work.delegate(task_id, role, objective, acceptance)` — создаёт durable-поручение к конкретной задаче; для специалиста требуется активное родительское поручение.
- `work.list(task_id)` — показывает цепочку и статусы поручений.
- `work.report(status, result, evidence)` — исполнитель сообщает проверяемый результат (`submitted`) или блокировку (`blocked`). Привязка к task_id, assignment id и роли проверяется сервером, версия ТЗ также.
- `work.review(assignment_id, action, reason)` — ПМ подтверждает результат (`completed`), повторяет после блокировки либо отменяет ещё не запущенное поручение.

## Исполнение

PostgreSQL v13 содержит очередь, роли, вложенность, версию ТЗ, результат, доказательства, состояние и число попыток. Каждое поручение исполняется собственным Temporal workflow `executeDelegatedWork` со стабильным ID для каждой попытки. При неуверенном ответе Temporal диспетчер восстанавливает тот же запуск, не создавая второй. Codex получает задачу и MCP-сессию с правами конкретной роли. Нужные действия выполняются через предусмотренные инструменты, а не через текстовые утверждения модели.

Ответ агента не является доказательством выполнения: если отсутствует успешный `work.report`, поручение становится заблокированным. Статус `submitted` требует отдельного просмотра ПМ и не переводит саму задачу в `done`. Для задач с изменениями кода остаются обязательными PR, QA, CI, слияние и условия выкладки. Браузерные и иные проверки остаются под своими доказательными шлюзами.

## Совместимость и границы

Существующие задачи и процессы разработки, тестирования, документации и прежний `browser_evidence` продолжают работать без миграции старых выполнений. Общие поручения добавлены в Центр процессов и `processes.list`. Новый процесс не выдаёт автоматически права на продакшен или сторонние сервисы; возможности зависят от доступных role-scoped инструментов и подключений. Там, где нужного инструмента ещё нет, специалист обязан вернуть `blocked` с требованиями к доступу. Полная замена специализированных маршрутов выполняется только после подтверждённого покрытия эквивалентных операций и регрессий.

## Проверки

Unit-тесты покрывают набор ролей и доступных MCP-инструментов, DDL, запрет запуска завершённой задачи, изоляцию задачи и версии ТЗ, запрет фиктивного completion и отсутствие прямого перехода Kanban. CI должен проверить TypeScript, архитектурные ограничения, все API-регрессии, Temporal и браузерный E2E. Реальный доступ к окружению целевого сайта этим PR не предоставляется; он должен настраиваться отдельно, по минимальным правам.

## Универсальные зависимости между поручениями (v14)

ПМ может создавать атомарный план через `work.plan(task_id,steps)`. Этапы не задаются строками или списком обязательных ролей: для каждого шага передаются уникальный `key`, исполнитель `role`, конкретная цель `objective`, проверяемый результат `acceptance` и список `needs` — ключей реально необходимых результатов. Например, QA зависит от подтверждённой подготовки тестовой среды DevOps, а документация может зависеть от приёмки QA. Параллельные независимые шаги запускаются одновременно в пределах ёмкости ролей.

- Проверка DAG без внешних эффектов исключает циклы, неизвестные зависимости, самозависимости, повторы ключей и слишком большие планы.
- PostgreSQL v14 создаёт `agent_work_plan_dependencies` с составными внешними ключами: зависимость не может ссылаться на поручение другого проекта или задачи.
- Диспетчер Temporal запускает шаг лишь после подтверждённого ПМ статуса `completed` каждого предшественника. `submitted` или `blocked` не считаются готовыми.
- ПМ следит за каждым шагом через имеющийся мониторинг Temporal, получает уведомление о блокировках и может использовать `work.review` для адресного повтора.
- `work.list` возвращает статусы и ссылки на предшественников, чтобы агент видел, чего ждёт задача. История, требования и результаты сохраняются; ни один шаг сам по себе не обходит PR/CI/QA.
