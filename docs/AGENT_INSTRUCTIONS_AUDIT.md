# Аудит инструкций AI-команды: переход к целевому исполнению

Выполнено 15.11.2026 по актуальному исходному коду `ai-development-orchestrator`.

## Источники инструкций и их ответственность

| Источник | Что должно оставаться | Что устранено / сокращено |
| --- | --- | --- |
| `prompt-assembler.mjs` | Единая недоверенная область данных, границы полномочий и доказательность результатов | Не дублируем эту политику в каждом профиле |
| `agent-instructions.ts` и «Команда» | Короткая специализация, стиль и основные критерии роли | Не задаёт обязательный маршрут по Kanban-колонкам и детальный вызов каждого API |
| `pm-goal-policy.ts` | Правило выбора цели, разрешений владельца, аварийных альтернатив и `goals.complete` | Убраны повторные предписания о каждой роли и полном цикле стадий |
| `pm-execution-guidance.ts` | Только действия ПМ: прямой инструмент / одно делегирование / DAG, фактические доказательства, повторы | Убран отдельный псевдо-workflow для screenshot-only и дублирование политики согласований |
| `pm-turn.ts` | Собирает зоны одного промпта, актуальный ответ/цель/события | Профиль отдельно от неизменяемой политики; история/ответы/приложения теперь данные `context`, а не инструкции `protocol` |
| `delegated-work-activities.ts` | Цель поручения, принятый контекст, инструменты, `work.report` | Повторные длинные списки ролей, шагов и generic-политик |
| `developer-prompt.mjs`, `qa-prompt.mjs`, `qa-tools.md` | Только специфические технические операции и машинный формат результата | Эти контракты НЕ убраны: они обеспечивают проверяемый PR/SHA, CI, QA и подлинность изображений |
| `agent-context.mjs` | Проверка `tasks.read` в устаревших reader-сессиях | Не приклеивает повторный префикс к уже размеченному промпту |
| `agent-memory.ts` и проектные записи | Подтверждённые применимые инструкции отдельно от наблюдений | История/память не имеют права подменять системную политику |

## Найденные проблемы

1. **Дубли и конкурирующие приказы.** ПМ получал длинные правила одновременно из редактируемого профиля, общей PM-политики, PM-execution guidance и общего сборщика. Приоритет было трудно понять человеку и модели.
2. **Привязка роли к этапу.** Тексты некоторых ролей описывали обязательную передачу дальше по pipeline, хотя Kanban теперь показывает состояние результата, а план может состоять из одного действия или независимых параллельных шагов.
3. **Неправильное положение пользовательских данных.** В `pm-turn` текст событий, ответов и приложений попадал в область протокольных инструкций; теперь передаётся в область данных без системного авторитета.
4. **Скриншоты ошибочно считались тестированием.** Для screenshot-only нужен browser-enabled Codex-исполнитель и две настоящие проверенные картинки, но не обязательно отдельный QA-цикл. Код, меняющий функциональность, по-прежнему проверяет независимый QA.
5. **Разница между дефолтами и правками владельца.** Настройки в таблицах команды сохраняются между выкладками. Изменение констант исходного кода само по себе не обновляет старые проекты.

## Принятое решение

Системные правила безопасности и проверки — в backend и Runner; модель может **выбирать план**, но не обходить эти ограничения. Профиль определяет компетенцию, а конкретное поручение определяет цель. В Kanban текущая работа отражается при постановке первого исполнительного процесса, а карточка показывает ответственную роль и содержание действия.

Укорочены только неизменённые стандартные профили. Механизм `reconcileProjectTeamProfiles` сравнивает инструкции с точными прежними шаблонами и проверяет отсутствие истории ручного редактирования. Пользовательские инструкции сохраняются без перезаписи. Старые образцы вынесены в `agent-instructions-legacy.ts` как **данные для миграции, не часть промпта**.

## Что сохранено намеренно

- Независимый QA для изменений кода, тестовые сценарии и real evidence;
- серверные проверки PR/CI/deployment/QA, границы прав и защита секретов;
- возможность отложить/отменить работу штатно без потери истории;
- роль ПМ как координатора цели; существующие Temporal и Codex Runner, без второго scheduler;
- согласованная подписка Codex CLI, без перехода на платный API;
- человеческие отчёты вместо технических дампов.

## Как проверять после выкладки

1. Задача остаётся в «Бэклоге» при создании или составлении предварительного плана. Первое фактическое поручение переводит её в «В работе», в карточке видно **кто и что делает**.
2. Скриншоты без изменений кода: одно поручение с доступным browser bridge → настоящие desktop/mobile JPEG → `work.review` → `work.complete_task(kind=screenshots)` → приёмка; отдельный QA не обязателен.
3. Изменение кода: разработка → самостоятельные проверки → независимый QA → PR/CI → разрешённое завершение.
4. Перезапуск приложения сохраняет пользовательские правки команды, обновляя только прежние системные дефолты.
5. При сбое QA/браузера модель сообщает реальную причину, не запускает новый круг стадий без изменения условий.

**Ограничение:** у PM-чата нет собственного изолированного Chromium/локальной рабочей копии. Прямой вызов браузера внутри PM потребовал бы переноса доверенной sandbox-границы. Для screenshot-only реализован один исполнитель в уже существующем Runner без независимого QA, что даёт тот же результат без опасного расширения прав PM.
