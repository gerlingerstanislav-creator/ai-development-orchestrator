# QA через существующий Codex Runner

QA использует тот же `apps/codex-runner`, что и разработка: временную копию PR, `codex exec` и Temporal. Не нужен второй QA сервис, Docker-сокет или отдельный платный API. Все проверки относятся к точному SHA PR.

## Что доступно

- Node.js/npm, Python 3, pip, venv, pytest и Git.
- Установка зависимостей в рабочую копию PR через npm и PyPI в рамках разрешённой сетевой политики.
- Локальные HTTP-серверы и API-тесты без реальных Telegram/погодных API. Для внешних сервисов QA создаёт моки/фикстуры.
- Запуск тестов из репозитория, сохранение команд, результатов и ошибок в QA-отчёте.

**Браузерные E2E сейчас недоступны в защищённой Linux-песочнице Codex.** В CI подтверждено, что Chromium падает с `SIGTRAP` из-за ограничений Codex seccomp; отключение Crashpad не помогло. Поэтому мы **не устанавливаем неработающий Chromium/Playwright в образ**, не используем режим `danger-full-access` и не считаем визуальные кейсы проверенными. Когда Codex выпустит безопасное исправление либо появится отдельное разрешённое браузерное окружение, поддержку можно добавить без переработки workflow. До этого визуальные сценарии должны иметь `blocked/tool_unavailable`.

## Защитные границы

QA получает отдельный профиль `ado-qa`. Профиль включает **оба** обязательных параметра: `permissions.ado-qa.network.enabled=true` и `features.network_proxy=true`. Proxy разрешает только:

- `registry.npmjs.org` (зависимости npm)
- `pypi.org` и `files.pythonhosted.org` (пакеты Python)
- `localhost` и `127.0.0.1` (локальные тестовые серверы)

Прямой доступ к приватным IP/внутренним именам Docker, произвольным сайтам и неразрешённым репозиториям запрещён. `allow_local_binding=false` сохраняет защиту от обращения к приватным подсетям. Upstream proxy для песочницы отключён, чтобы она не использовала прокси аутентификации Codex.

Разработка по-прежнему использует профиль `ado-task` **без сетевого доступа**. Секреты Codex, GitHub, базы, `.git`, чужие рабочие каталоги и Docker-сокет не выдаются QA; git clone/PR выполняет доверенная часть Runner вне песочницы. Изоляцию нельзя ослаблять `dangerously-bypass-approvals-and-sandbox`.

Не устанавливайте произвольные глобальные утилиты из QA и не запрашивайте доступ к Docker-сокету. Если проверке необходим Docker, внешняя БД, реальный Telegram API или другой внешний ресурс — отмечайте сценарий `blocked` и используйте моки/фикстуры, когда возможно. Система не должна считать `failed` Codex (код 1, сбой авторизации/песочницы) подтверждением недоступности инструментов для тестирования.

Codex добавляет сетевые переменные окружения в каждую sandbox-команду и может обнулить `NO_PROXY` из настроек профиля. Для локальных HTTP-тестов передавайте исключение **непосредственно команде**:

```bash
env NO_PROXY=localhost,127.0.0.1,::1 no_proxy=localhost,127.0.0.1,::1 npm test
```

Это не отключает прокси для npm/PyPI, а позволяет клиенту обратиться к собственному локальному серверу. ПМ не обязан знать этот нюанс — он включён в инструкции QA. Безопасность исключений проверяется в CI.

## Проверка после обновления

1. CI выполняет Docker image build и `apps/codex-runner/isolation-smoke.mjs`: изоляция секретов и Git, npm registry, запрет прямого внешнего TCP, временный loopback HTTP и Python venv/pytest.
2. В запущенном приложении попросите ПМа повторить QA существующего PR. Temporal должен создать новый QA-цикл, показывать этап и сохранить результаты проверки.
3. QA должен записать `checks`, `caseResults` и `capabilities` для конкретного SHA. При настоящих дефектах возвращает задачу разработчику; при доказанной недоступности оставшихся сценариев — `blocked` и запрос согласования, но не автоматический пропуск.

**Ограничение:** для проектов, которым нужна полноценная распределённая среда (PostgreSQL, Redis, Docker Compose), только доступ к npm/PyPI и loopback не заменяет отдельный тестовый стенд. Такой сценарий пока считается `blocked`, без обхода QA.
