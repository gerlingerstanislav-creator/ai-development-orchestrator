# Knowledge Management — проектная документация и контекст агентов

## Источник истины

Техническое задание существует как дерево самостоятельных документов внутри системного корня «Техническое задание». Корневые и существующие документы не переписываются при миграции. Страницы имеют версии, статус знаний (\`draft\`, \`review\`, \`approved\`, \`obsolete\`) и метаданные. В контекст агентов попадают только \`approved\`.

Составное ТЗ выгружается в Markdown. Ссылки на разделы Markdown используют устойчивые UUID, вычисленные по структурному пути заголовка и его номеру среди одноимённых заголовков. Вставка абзацев перед разделом не меняет идентификатор. Переименование или перемещение под другой заголовок меняет адрес; версии документа при этом сохраняются.

## Инструкции

Используются существующие обязательные \`project_rules\` и инструкции этапа Workflow плюс модульные \`knowledge_instruction_modules\`. Модули могут быть общими для проекта или этапа; утверждённые обязательные применяются всегда, условные — по явно переданным тегам и тегам отобранных документов. Модель не маршрутизируется регулярными выражениями. Поведение сервисного доступа, безопасности и обязательных проверок остаётся серверным.

Черновики и устаревшие инструкции никогда автоматически не включаются. Изменение модулей доступно авторизованному администратору; применяется проверка номера ревизии. Актуальные инструкции можно редактировать в разделе «Документация».

## Контекст

\`buildKnowledgeContext\` получает проект, задачу, роль/этап и при необходимости идентификатор процесса, использует связанные с задачей документы и полнотекстовый поиск. Возвращает только краткие метаданные или ограниченные выдержки. Обязательные правила не обрезаются в угоду бюджету: бюджет ограничивает только необязательные материалы.

Сборщик вызывается в Temporal Activities разработки, тестирования, подготовки QA-планов и сверки требований. Читаемые данные и инструкции фиксируются в \`knowledge_context_snapshots\` с версиями документов; дополнительные вызовы \`knowledge.read\` / \`knowledge.section\` попадают в \`knowledge_context_reads\`. Историю можно открыть в «Центре процессов». Запись источников — не доказательство, что модель учла каждое требование.

## Трассировка

\`knowledge_task_links\`: связи документа/требования с задачей. \`knowledge_artifact_links\`: связь документа с QA-кейсом, PR или путём компонента. При завершении разработки PR привязывается к связанным документам, а после подготовки тест-плана добавляются связи с его тест-кейсами. Проектная принадлежность проверяется на сервере.

## Актуализация

После слияния PR технический писатель продолжает автоматически обновлять управляемый сервисом документ «Реализованные возможности». Для связанных тематических страниц он может сформировать \`knowledge_document_updates\`. Такие изменения проходят согласование: принятие версии проверяет неизменность исходного документа; устаревшее предложение отклоняется и задачу можно повторно отправить на подготовку.

Задача остаётся в этапе «Документация», пока есть ожидающие решения предложения. После решения последнего предложения завершается. Вопросы и изменения поведения, требующие решения владельца продукта, нельзя без согласования превращать в утверждённые требования.

## Границы

Поиск основан на PostgreSQL FTS, явных связях и метаданных. Векторный поиск, embeddings и полноценная оценка смысловой релевантности ещё не реализованы. Никаких дополнительных оплачиваемых API не требуется. Реальный smoke-тест исполнения Codex в развёрнутой среде выполняется отдельно; CI проверяет сборку, TypeScript и PostgreSQL-интеграции.
