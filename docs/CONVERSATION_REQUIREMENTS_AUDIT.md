## Найденные при этой проверке дефекты

1. Ответ пользователя не инициировал реальную новую аналитическую сверку, если предыдущий результат `needs_approval` уже существовал для той же версии ТЗ и SHA. Исправлено для неопределённых (`uncertain`) заключений. Существенные изменения по-прежнему требуют решения пользователя.
2. Ветка задачи могла быть создана Codex в GitHub при неудачном запуске раньше, чем поле `tasks.git_branch` успевало заполняться. Отмена теперь учитывает историю запусков и проверяет UUID-ветку.
3. Признак «QA-процесс активен» мог скрывать кнопку повторного тестирования, хотя backend имел механизм восстановления зависшего запуска. В закреплённой полоске доступна проверка/восстановление, а сервер при этом не допускает второго активного исполнителя.
4. Ответ на вопрос перезаписывал поле первоначального автора в базе. Для ответа добавлено отдельное `answered_by`.

## Границы подтверждения

- GitHub Actions проверяют сборку, TypeScript и PostgreSQL-тесты. Добавлены регрессионные тесты ответов аналитику и безопасности удаления GitHub-артефактов с подменой ответов GitHub API.
- Реальная очистка PR/ветки на тестовом GitHub-репозитории и полный запуск задачи через Temporal/Codex в этой проверке не проводились. Нельзя утверждать, что эти сценарии испытаны целиком.
- GitHub API позволяет **закрыть** PR, но не стереть его историю.
- Очистка GitHub и транзакция PostgreSQL не являются одной распределённой транзакцией; при частичном сбое нужно безопасно повторить операцию и проверить аудит.
- Исторические документы без сохранённого источника нельзя удалять автоматически без угрозы общей документации.
- Универсальный запуск приложения и браузерное визуальное тестирование по-прежнему требуют отдельного механизма.

## Следующие проверяемые сценарии

1. На изолированной задаче: анализ с вопросами → ответ → повторная сверка → разработка → генерация QA-плана → результат проверки → слияние → документация.
2. Остановка Codex после создания UUID-ветки, до появления PR: безопасная отмена и проверка удаления осиротевшей ветки.
3. QA-процесс, завершённый в Temporal, но оставивший старый активный статус в PostgreSQL: проверка/восстановление без второго исполнителя.
4. Убедиться, что общие кейсы и документы остаются после отмены другой задачи, а журнал отмены фиксирует реально удалённое.


## Доработка: Менеджер проекта

Согласована и реализована отдельная роль единственного собеседника заказчика с узким контекстом. У специалистов независимые компетенции, инструкции и коммуникации. Блокирующие вопросы направляются Менеджеру; недоступные визуальные сценарии QA нельзя считать успешными. Пользователь выбирает разрешение слияния с ограничениями или ожидание инструментов. Возможность восстановить зависшую старую задачу с существующим PR реализована без обязательного создания новой.
