# Архитектура AI Development Orchestrator

Обновлено: 9 ноября 2026 года. Описывает утверждённый стек и состояние репозитория, а не перечень вариантов для обсуждения.

## Стек и границы ответственности

- **apps/web** — React + TypeScript + Vite: проекты, Kanban, задачи, документация, каталог QA, история процессов, настройки workflow.
- **apps/api** — Node.js + TypeScript + Fastify: REST API, авторизация, PostgreSQL, интеграция GitHub, правила и документы, запуск Temporal.
- **PostgreSQL** — проекты, документы, сценарии, кейсы, QA-планы, результаты, задачи, события и настройки.
- **Temporal** — долговечный workflow «разработка → аналитическая сверка ТЗ → подготовка QA → независимое тестирование → исправление», с журналом переходов. В локальном Compose работает dev-сервер с сохраняемым томом, не production-кластер.
- **apps/codex-runner** — исполнитель Codex CLI в выделенном контейнере. Авторизуется через обычную подписку ChatGPT; проект не требует отдельного платного OpenAI API. Git-операции выполняются сервисом вне команд агента.
- **GitHub** — код, ветки задач, PR, CI и слияние.
- **Docker Compose** — локальные сервисы приложения и инфраструктура.

## Согласованный жизненный цикл задачи

Анализ → Разработка → Тестирование → Ожидает слияния → Документация → Готово.

Подготовка полной тестовой документации выполняется QA-агентом перед тестированием, после работы разработчика и отдельной сверки PR с ТЗ аналитиком. Оба действия исполняются Temporal как внутренние этапы и не добавляют колонок Kanban.

1. Аналитик формирует требования и критерии приёмки, человек утверждает ТЗ.
2. Разработчик создаёт изменения и PR по утверждённым требованиям.
3. Аналитик изучает PR и сравнивает реальное поведение с текущим ТЗ и его версиями. Технические уточнения обновляет автоматически; изменения поведения требуют согласования пользователя.
4. Если существенное изменение отклонено, задача возвращается разработчику. Если подтверждено, ТЗ получает новую версию.
5. QA создаёт или актуализирует User Flows, тест-кейсы и регрессию по согласованному ТЗ, с учётом изменений PR без подгонки ожидаемых результатов под реализацию.
6. Независимый тестировщик исполняет проверки. Запуск привязан к версии ТЗ и снимку тест-плана.
7. Слияние допустимо, только если версия ТЗ, QA-план, результат тестирования и SHA проверенного PR согласованы.
8. После слияния обновляется документация и задача завершается.

История требований хранится в task_spec_versions, предложения аналитика — task_requirement_reviews, отдельные запускаемые проверки требований — requirement_review_runs. Актуальная версия и статус сверки находятся в tasks. Ручная правка ТЗ на любом этапе создаёт новую версию и инициирует проверку аналитика.

В Kanban «Разработка», «Тестирование» и «Ожидает слияния» объединены в общую группу «Разработка».

## Модель QA-документации

- **qa_user_flows** — переиспользуемые пользовательские сценарии и их предусловия/шаги.
- **qa_test_cases** — переиспользуемые тест-кейсы (действия, ожидаемые результаты, приоритет, категория, применимость к автоматизации). Существующие ожидания не должны молча переписываться под новую реализацию.
- **qa_test_plans** — привязка набора проверок к утверждённому ТЗ задачи и его отпечатку.
- **qa_plan_cases** — связь кейсов с планом (targeted или regression); обязательные smoke-кейсы добавляются программно.
- **qa_case_results** — проверяемые результаты отдельных кейсов, привязанные к конкретному запуску AI-тестирования.
- **qa_manual_results** — отдельные наблюдения человека; не выдаются за AI-прогон.
- **qa_case_versions** — история редактирования человеком.

Все записи привязаны к проекту; управление доступом применяется в API. Формирование AI-планов требует подключённого Codex.

## Проверяемость и согласованное исключение

QA-агент проверяет фактически доступные инструменты в изолированном Codex-контейнере, выполняет все выполнимые проверки и фиксирует доказательства по каждому кейсу. Для отсутствующего браузера, среды или ручной процедуры он возвращает blocked/not_run с причиной (tool_unavailable, environment_unavailable, manual_only) и конкретным объяснением.

Если тесты заблокированы **только отсутствием инструментов**, а подтверждённых ошибок и провалившихся проверок нет, задача остаётся на этапе «Тестирование». В карточке задачи показываются выполненные и непроверенные сценарии. Администратор может явно согласовать переход в очередь слияния, указав причину и подтвердив риск. Это не означает, что непроверенные сценарии пройдены.

Согласование хранится в qa_merge_waivers с идентификатором QA-запуска, утверждённой версией ТЗ, SHA PR, списком непроверенных сценариев, пользователем и обоснованием. Проверка merge повторно сверяет последние QA-результаты и SHA; CI и GitHub branch protection не обходятся. Новая версия требований, повторный QA-запуск или коммит PR обесценивают старое разрешение.

Сбой тестового исполнителя, отсутствие доказательств и подтверждённые дефекты **не могут** быть основанием для такого исключения: нужно исправить проблему или повторить проверку.

## Единый ход работ по задаче

Один полноценный цикл Temporal (разработка → сверка ТЗ → подготовка QA → тестирование) **эксклюзивно владеет задачей**. PostgreSQL-таблица `task_orchestration_owners` с уникальным `task_id` не позволяет параллельно запускать ручной QA, пока автоматический цикл ещё анализирует требования или формирует кейсы. Освобождение права выполняется в `finally` workflow; старые запуски до миграции дополнительно проверяются в Temporal.

Карточка задачи имеет один журнал справа. API `GET /projects/:id/tasks/:taskId/activity` объединяет `task_events`, `process_events` (разработка, анализ, подготовка QA, проверка) и состояние эксклюзивного цикла, с фильтрацией по конкретной задаче и её проекту. Журнал обновляется во время открытой задачи, включая ожидание согласования. Решения аналитика и обработка недоступных QA-проверок доступны справа вместе с перепиской, а не в отдельной левой панели.

Ручной запуск повторного тестирования запрещён во время активного цикла. Если тестировщик возвращает неправильный JSON, исполнитель запрашивает форматирование отчёта по JSON Schema повторно, не подменяя отсутствие доказательств успехом. При повторной ошибке сохраняется сообщение об ошибке и задача остаётся на тестировании; она не передаётся разработчику как дефект приложения.

## Ограничения текущей реализации

- Тест-дизайн основывается на утверждённых требованиях, правилах и ограниченном контексте, а не на семантическом индексе всего проекта.
- Сверка ТЗ и подготовка QA-плана используют Codex CLI; сбой контрольной точки не означает, что уже законченный код нужно разрабатывать заново.
- Исполнитель тестов не предоставляет полноценный браузер или развернутую среду приложения. Он не должен утверждать, что проверил E2E без запуска соответствующего инструмента.
- Отсутствует полноценный изолированный E2E Test Runner; в дальнейшем можно подключить Playwright, интеграционные тесты и CI-артефакты.
- QA-план хранит текущую подборку кейсов; каждый запуск тестирования дополнительно сохраняет снимок плана и версию ТЗ.
- Полная матрица покрытия/impact analysis пока не реализована.
- Перезапуск Codex-контейнера может прервать активную команду, несмотря на сохранение истории Temporal; production-развёртывание требует дальнейшей работы над изоляцией, очередями, безопасностью и наблюдаемостью.

## Принципы

- Задача не равна запуску агента: попыток может быть несколько.
- Бизнес-этап не равен работающему процессу; этап может ожидать подтверждение или лимит.
- Требования и критерии приёмки формируются до реализации, подробные тест-кейсы — после сверки ТЗ с реализацией; тест не должен подгоняться под код.
- Внешние эффекты (commit, push, PR, merge) должны быть идемпотентными и проверять SHA.
- Секреты не записываются в документацию и не передаются текстом в инструкции AI.
- Пользователь видит историю и может вручную скорректировать тест-кейсы или записать результат проверки.
