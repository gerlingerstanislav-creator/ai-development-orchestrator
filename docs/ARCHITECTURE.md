# Архитектура AI Development Orchestrator

Обновлено: 9 ноября 2026 года. Описывает утверждённый стек и состояние репозитория, а не перечень вариантов для обсуждения.

## Стек и границы ответственности

- **apps/web** — React + TypeScript + Vite: проекты, Kanban, задачи, документация, каталог QA, история процессов, настройки workflow.
- **apps/api** — Node.js + TypeScript + Fastify: REST API, авторизация, PostgreSQL, интеграция GitHub, правила и документы, запуск Temporal.
- **PostgreSQL** — проекты, документы, сценарии, кейсы, QA-планы, результаты, задачи, события и настройки.
- **Temporal** — долговечный workflow «разработка → аналитическая сверка ТЗ → подготовка QA → независимое тестирование → исправление», с журналом переходов. В локальном Compose работает dev-сервер с сохраняемым томом, не production-кластер.
- **apps/codex-runner** — исполнитель Codex CLI в выделенном контейнере. Авторизуется через обычную подписку ChatGPT; проект не требует отдельного платного OpenAI API. Git-операции выполняются сервисом вне команд агента.
- **GitHub** — код, ветки задач, PR, CI и слияние.
- **Docker Compose** — локальные сервисы приложения и инфраструктура.

## Согласованный жизненный цикл задачи

Анализ → Разработка → Тестирование → Ожидает слияния → Документация → Готово.

Подготовка полной тестовой документации выполняется QA-агентом перед тестированием, после работы разработчика и отдельной сверки PR с ТЗ аналитиком. Оба действия исполняются Temporal как внутренние этапы и не добавляют колонок Kanban.

1. Аналитик формирует требования и критерии приёмки, человек утверждает ТЗ.
2. Разработчик создаёт изменения и PR по утверждённым требованиям.
3. Аналитик изучает PR и сравнивает реальное поведение с текущим ТЗ и его версиями. Технические уточнения обновляет автоматически; изменения поведения требуют согласования пользователя.
4. Если существенное изменение отклонено, задача возвращается разработчику. Если подтверждено, ТЗ получает новую версию.
5. QA создаёт или актуализирует User Flows, тест-кейсы и регрессию по согласованному ТЗ, с учётом изменений PR без подгонки ожидаемых результатов под реализацию.
6. Независимый тестировщик исполняет проверки. Запуск привязан к версии ТЗ и снимку тест-плана.
7. Слияние допустимо, только если версия ТЗ, QA-план, результат тестирования и SHA проверенного PR согласованы.
8. После слияния обновляется документация и задача завершается.

История требований хранится в task_spec_versions, предложения аналитика — task_requirement_reviews, отдельные запускаемые проверки требований — requirement_review_runs. Актуальная версия и статус сверки находятся в tasks. Ручная правка ТЗ на любом этапе создаёт новую версию и инициирует проверку аналитика.

В Kanban «Разработка», «Тестирование» и «Ожидает слияния» объединены в общую группу «Разработка».

## Модель QA-документации

- **qa_user_flows** — переиспользуемые пользовательские сценарии и их предусловия/шаги.
- **qa_test_cases** — переиспользуемые тест-кейсы (действия, ожидаемые результаты, приоритет, категория, применимость к автоматизации). Существующие ожидания не должны молча переписываться под новую реализацию.
- **qa_test_plans** — привязка набора проверок к утверждённому ТЗ задачи и его отпечатку.
- **qa_plan_cases** — связь кейсов с планом (targeted или regression); обязательные smoke-кейсы добавляются программно.
- **qa_case_results** — проверяемые результаты отдельных кейсов, привязанные к конкретному запуску AI-тестирования.
- **qa_manual_results** — отдельные наблюдения человека; не выдаются за AI-прогон.
- **qa_case_versions** — история редактирования человеком.

Все записи привязаны к проекту; управление доступом применяется в API. Формирование AI-планов требует подключённого Codex.

## Проверяемость и согласованное исключение

QA-агент проверяет фактически доступные инструменты в изолированном Codex-контейнере, выполняет все выполнимые проверки и фиксирует доказательства по каждому кейсу. Для отсутствующего браузера, среды или ручной процедуры он возвращает blocked/not_run с причиной (tool_unavailable, environment_unavailable, manual_only) и конкретным объяснением.

Если тесты заблокированы **только отсутствием инструментов**, а подтверждённых ошибок и провалившихся проверок нет, задача остаётся на этапе «Тестирование». В карточке задачи показываются выполненные и непроверенные сценарии. Администратор может явно согласовать переход в очередь слияния, указав причину и подтвердив риск. Это не означает, что непроверенные сценарии пройдены.

Согласование хранится в qa_merge_waivers с идентификатором QA-запуска, утверждённой версией ТЗ, SHA PR, списком непроверенных сценариев, пользователем и обоснованием. Проверка merge повторно сверяет последние QA-результаты и SHA; CI и GitHub branch protection не обходятся. Новая версия требований, повторный QA-запуск или коммит PR обесценивают старое разрешение.

Сбой тестового исполнителя, отсутствие доказательств и подтверждённые дефекты **не могут** быть основанием для такого исключения: нужно исправить проблему или повторить проверку.

## Единый ход работ по задаче

Один полноценный цикл Temporal (разработка → сверка ТЗ → подготовка QA → тестирование) **эксклюзивно владеет задачей**. PostgreSQL-таблица `task_orchestration_owners` с уникальным `task_id` не позволяет параллельно запускать ручной QA, пока автоматический цикл ещё анализирует требования или формирует кейсы. Освобождение права выполняется в `finally` workflow; старые запуски до миграции дополнительно проверяются в Temporal.

Карточка задачи имеет один журнал справа. API `GET /projects/:id/tasks/:taskId/activity` объединяет `task_events`, `process_events` (разработка, анализ, подготовка QA, проверка) и состояние эксклюзивного цикла, с фильтрацией по конкретной задаче и её проекту. Журнал обновляется во время открытой задачи, включая ожидание согласования. Решения аналитика и обработка недоступных QA-проверок доступны справа вместе с перепиской, а не в отдельной левой панели.

Ручной запуск повторного тестирования запрещён во время активного цикла. Если тестировщик возвращает неправильный JSON, исполнитель запрашивает форматирование отчёта по JSON Schema повторно, не подменяя отсутствие доказательств успехом. При повторной ошибке сохраняется сообщение об ошибке и задача остаётся на тестировании; она не передаётся разработчику как дефект приложения.

## Ограничения текущей реализации

- Тест-дизайн основывается на утверждённых требованиях, правилах и ограниченном контексте, а не на семантическом индексе всего проекта.
- Сверка ТЗ и подготовка QA-плана используют Codex CLI; сбой контрольной точки не означает, что уже законченный код нужно разрабатывать заново.
- Исполнитель тестов не предоставляет полноценный браузер или развернутую среду приложения. Он не должен утверждать, что проверил E2E без запуска соответствующего инструмента.
- Отсутствует полноценный изолированный E2E Test Runner; в дальнейшем можно подключить Playwright, интеграционные тесты и CI-артефакты.
- QA-план хранит текущую подборку кейсов; каждый запуск тестирования дополнительно сохраняет снимок плана и версию ТЗ.
- Полная матрица покрытия/impact analysis пока не реализована.
- Перезапуск Codex-контейнера может прервать активную команду, несмотря на сохранение истории Temporal; production-развёртывание требует дальнейшей работы над изоляцией, очередями, безопасностью и наблюдаемостью.

## Принципы

- Задача не равна запуску агента: попыток может быть несколько.
- Бизнес-этап не равен работающему процессу; этап может ожидать подтверждение или лимит.
- Требования и критерии приёмки формируются до реализации, подробные тест-кейсы — после сверки ТЗ с реализацией; тест не должен подгоняться под код.
- Внешние эффекты (commit, push, PR, merge) должны быть идемпотентными и проверять SHA.
- Секреты не записываются в документацию и не передаются текстом в инструкции AI.
- Пользователь видит историю и может вручную скорректировать тест-кейсы или записать результат проверки.



## Комментарии между агентами и действия задачи

Текущая архитектура дополнена task-scoped хранилищем `task_agent_notes`: автор и этап, адресат, вид сообщения, версия процесса, состояние вопроса и ответ человека. Агент получает только адресованные ему и общие комментарии; они не являются изменением утверждённого ТЗ. Сервер отклоняет продолжение при незакрытых вопросах, даже если UI отправил запрос перехода. Обновлённые требования по ответу повторно проходят аналитическую сверку.

Все пользовательские разрешённые действия живут в закреплённой полоске под лентой переписки и над полем ввода, а не внутри истории. Хронология сохраняет сообщения и журналы агентов и QA.

Отмена несленой задачи проверяет GitHub/Temporal/зависимости и очищает только атрибутированные ей объекты. Сведения об отмене сохраняются в аудите. Подробности и ограничения: [TASK_COLLABORATION.md](TASK_COLLABORATION.md).


## Менеджер проекта как единственный интерфейс заказчика

Добавлена роль **Менеджер проекта** с ограниченным контекстом (состояние, подтверждённые отчёты, открытые решения и небольшая часть переписки). Он не является единой моделью со всем кодом. Специалисты сохраняют собственные инструкции и независимые результаты. `manager_messages` хранит входящие обращения до завершения работы Codex, `manager_requests` — решения с привязкой к артефактам. Temporal workflow `projectManagerReply` запускает обработку обращения и обмен внутренними вопросами специалистов.

Менеджер просит только принципиальные решения. Недоступность визуальных инструментов отражается в QA как непроверенные кейсы и выносится на явное согласование, которое проходит существующий строгий waiver gate, не подменяя тестовые результаты.

## Диалог аналитика, импорт и структура документации

Пользовательский чат аналитика работает в двух разных режимах. **Вопросы, обсуждение и критика структуры** используют обычный текстовый ответ Codex с контекстом фактического дерева документов и выдержками из существующих страниц. Они не запускают Temporal, не требуют JSON-операций и не изменяют документы. **Явные команды создания, редактирования и импорта** остаются исполняемыми процессами с контролем доступа и журналом событий.

Импорт Markdown сохраняет и тематические страницы, и **полные оригиналы исходных файлов** в разделе «Исходные материалы и исследования». Исходники сгруппированы по стабильному ключу импорта и привязаны к закреплённому SHA GitHub; повторный импорт не создаёт копий и не перезаписывает ручные правки, а предлагает изменения на согласование. Исходные разделы, исключённые из синтеза ТЗ, не теряются. Тематические документы направляются в соответствующий системный раздел (ТЗ, архитектура, эксплуатация, дизайн, исследования); необычно большие сквозные темы повторно декомпозируются по контрольным точкам без потери ранее записанных частей.

Явная команда **реорганизовать документацию** запускает отдельный Temporal-процесс: аналитик строит JSON-план размещения *существующих импортированных тематических страниц*, а сервер валидирует все UUID и применяет изменения одной транзакцией. При необходимости создаются навигационные группы с устойчивыми идентификаторами. Содержание, ссылки на источники, ID страниц, утверждённые решения и документы, размещённые пользователем в собственные папки, сохраняются. Для старых импортов исходные файлы восстанавливаются из сохранённых `document_import_jobs.source_snapshot` без повторного чтения GitHub. Корневые системные разделы не меняются.


## Пересборка ТЗ по согласованной структуре

Вопрос о качестве структуры документации обрабатывается как обычный разговор. Явная просьба **переписать или пересобрать текущее ТЗ по ранее предложенной структуре** запускает отдельную ветвь `runDocumentationJob` через Temporal, а не простой чат и не перемещение страниц.

Сервис `documentation-rebuild.ts` выполняет следующие шаги:

1. Снимает **полную неизменяемую копию текстов** существующих импортированных тематических страниц в `document_import_jobs.rebuild_sources` и строит проверяемый предметный план `rebuild_plan` с учётом предыдущего предложения аналитика из диалога. Все исходные страницы должны быть покрыты планом; идентификаторы проверяются сервером.
2. Переписывает материалы в новые страницы небольшими фрагментами. Сохраняет `document_import_topics.cursor`, `draft_body` и `rebuild_questions` после каждого фрагмента. Записанные части и уже завершённые страницы не генерируются повторно при возобновлении того же процесса.
3. Публикует новый документ с критериями, вопросами к ПО, ссылками на старые страницы и сохранённые GitHub-источники. Изменения страницы и контрольной точки атомарны.
4. **Только после завершения всех новых страниц** переносит старые импортированные страницы в папку «Предыдущая версия ТЗ» внутри раздела исходных материалов. Старые UUID, тексты, ссылки, вложения и вопросы не уничтожаются. Если страница была изменена во время процесса, она остаётся на месте, а результат сообщает об исключении.
5. Для старых импортов при необходимости восстанавливает исходные Markdown-файлы из сохранённых снимков без повторного импорта `ideas`.

Процесс **не создаёт задачи разработки** и не меняет `ideas`. Структура из ответа AI не принимается без серверной проверки полноты и уникальности. Содержательная проверка того, что новый текст не упустил требований, остаётся задачей продуктового ревью: детерминированные CI-тесты доказывают сохранность данных и возобновляемость, но не качество формулировок реального Codex.


## Согласованный запуск разработки

План разработки, карточка и ПМ записывают поручения через одну команду. Для каждой задачи очередь хранит версию ТЗ, идентификатор попытки и, если задача входит в итерацию, её согласованную ревизию. Карточка возвращает приём в очередь. Фактическое начало видно в Центре процессов.

Диспетчер выбирает готовую задачу с наивысшим приоритетом и повторно проверяет ревизию, версию ТЗ, вопросы, зависимость и наличие слота перед резервированием цикла. Задачи, которые ждут, не ограничивают выборку готовых. В Центре процессов отображается причина ожидания. Открытый PR задачи-основания допускает старт с её ветки. После слияния задачи-основания берётся целевая ветка проекта.

Если итерация, принадлежность задачи или версия ТЗ изменилась до резервирования, поручение требует повторного запуска владельцем. При обновлении старые ожидающие записи без ревизии также требуют подтверждения. Зарезервированные и работающие циклы сохраняют свой идентификатор. Временный сбой передачи в Temporal оставляет запись для повторной доставки под тем же идентификатором.

Проверка доступа к ветке и PR выполняется в цикле до запуска Codex. Если изменения уже есть в ветке задачи и исправления не требуются, цикл может восстановить PR и продолжить со сверки ТЗ.

## Восстановление Runner и пакетного слияния

Отсчёт лимита попытки начинается при занятии слота Runner. Разработка получает до 30 минут, тестирование и разрешение конфликтов до 15 минут. При превышении лимита Runner останавливает активную группу процессов, завершает текущую попытку и освобождает слот. Запись содержит последний шаг и допускает одну попытку восстановления с тем же идентификатором и сохранённым состоянием. Повторный таймаут завершает работу с ошибкой, видимой в Центре процессов. Ожидание свободного исполнителя и ожидание решения владельца идут отдельно.

Runner сохраняет идентификатор, состояние и результат попытки в постоянном томе `codex_jobs`. Входной запрос и токен GitHub в журнал не записываются. После перезапуска Temporal передаёт незавершённое задание с прежним ID. Перед `git push` Runner сохраняет исходный и новый SHA. Если новый коммит уже в GitHub, Runner использует существующий PR или создаёт его без повторного запуска Codex. При постороннем изменении ветки задание требует проверки. Если изменения остались только в удалённой при перезапуске рабочей копии, Codex повторяет работу с опубликованной ветки. QA сохраняет SHA и повторяет проверку только для того же коммита и версии ТЗ.

Запрос пакетного слияния сохраняет список задач в PostgreSQL. Temporal обрабатывает их последовательно, сначала задачи-основания. Прогресс, результат каждого PR и итоговый статус доступны после перезапуска API. После потери ответа GitHub следующий шаг проверяет состояние PR. Если PR уже слит, система фиксирует результат и продолжает обработку. Для частично успешного пакета Центр процессов показывает отдельный статус.

При обновлении существующие пакетные запуски, для которых прежняя версия хранила список задач только в памяти, получают статус ошибки с предложением повторить запуск для оставшихся PR. Старые попытки без журнала подхватываются по существующему PR, когда его можно восстановить. Для старого QA без закреплённого SHA нужен новый прогон.

## Допуск PR к слиянию

Одиночное и пакетное слияние используют один серверный допуск. Для любого открытого PR нужны сверка текущей версии ТЗ с его SHA, актуальный QA-план и завершённый отчёт для этого SHA, версии и плана. Исключение применяется только для допустимых ограничений QA, согласованных владельцем для конкретного прогона. Старую задачу без доказательств можно вернуть на проверку кнопкой «Повторить сверку ТЗ и QA» в карточке.

Сервис читает обязательные проверки из защиты целевой ветки и GitHub Rulesets. Перед слиянием он показывает имена отсутствующих, незавершённых, неуспешных или недоступных проверок. Источник проверяется по GitHub App там, где его возвращают правила. Если GitHub сообщает проверки для тестового коммита слияния, обязательные проверки оцениваются на нём. В запрос слияния передаётся SHA проверенного PR. Дополнительные правила ветки применяет GitHub.

## Изоляция исполнения

API подписывает пользовательские сессии через `JWT_SECRET`. API, Temporal worker и Runner используют отдельный `RUNNER_SHARED_SECRET` для внутренних запросов. При обновлении установите новый секрет в `.env` до пересоздания контейнеров.

Рабочие команды запускаются в Linux sandbox Codex. Каждое задание получает свою копию репозитория и собственный каталог для временных файлов. Сеть команд выключена, метаданные `.git` доступны для чтения. Авторизованный процесс Codex обращается к ChatGPT отдельно, а доверенный Runner делает GitHub-запросы и push. Git запускается с отключёнными hooks и fsmonitor. У разговорных агентов остаётся проектный MCP с ограниченными правами сессии, shell отключён.

Runner работает без Linux capabilities и с `no-new-privileges`. Для вложенного bubblewrap только сервис Runner использует расширенный профиль seccomp. Для Runner Compose по умолчанию задаёт `apparmor:unconfined`, чтобы разрешить монтирования внутри user namespace. На хостах с ограничением AppArmor на создание пользовательских пространств имён загрузите `sudo apparmor_parser -r docker/runner-userns.apparmor` и установите `RUNNER_APPARMOR_PROFILE=ado-runner-userns`. На хосте должны быть разрешены непривилегированные user namespaces. При ошибке проверки sandbox Runner сообщает причину и прекращает задание.
