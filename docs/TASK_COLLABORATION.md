# Рабочие сообщения и контрольные точки задачи

## Единая переписка

Карточка задачи показывает одну хронологическую историю: обращения пользователя, результаты анализа, шаги разработки и QA, системные события и рабочие комментарии других агентов. У каждого комментария указан **автор** и **адресат**, комментарии имеют назначение `handoff`, `observation`, `risk`, `question` или `resolution`.

**Рабочий комментарий не является изменением утверждённого ТЗ.** Разработчик может предупредить тестировщика о техническом нюансе, тестировщик — сообщить разработчику шаги воспроизведения, аналитик — отметить неоднозначность. Контекст хранится в `task_agent_notes` и передаётся адресатам с ограниченным объёмом. Одно событие исполнения создаёт не более одного одинакового комментария (`source_key`).

Новые агенты получают только сообщения этой задачи, адресованные их этапу либо всем участникам. Такие сообщения рассматриваются как *непроверенный рабочий контекст*, а не как новые инструкции с приоритетом над требованиями, политикой безопасности или правилами проекта.

Постоянная документация не должна автоматически копировать рабочие заметки. В документацию попадают только проверенные и утверждённые решения по уже реализованной функциональности.

## Блокирующие вопросы

Вопрос имеет статус `open` и отображается в переписке с указанием автора. Под перепиской появляется действие «Ответить на вопрос». После ответа сохраняются текст, пользователь и время; стадия анализа должна повторно сверить влияние ответа на утверждённое ТЗ.

Переходы между анализом, разработкой, тестированием, слиянием и документированием **проверяют наличие открытых вопросов на сервере**. Задачу нельзя пропустить дальше просто перетаскиванием в Kanban или нажатием кнопки. Незаполненные критерии приёмки и требование согласования изменений также остаются блокирующими.

## Компактная панель действий

В правой колонке окна задачи: единый прокручиваемый журнал, затем закреплённая **непрокручиваемая относительно истории** панель допустимых действий, затем поле ввода сообщения. В панели показывается краткая причина ожидания и только релевантные текущей стадии действия: анализ, запуск разработки, повторный QA, подтверждение/отклонение требований, согласование пропуска недоступных проверок, слияние, документирование, рабочий комментарий, ответ на вопрос и отмена задачи.

Проверка доступности кнопок в UI служит подсказкой. Авторитетное ограничение переходов и проверка фактического SHA PR остаются на backend. Визуально сообщения разных ролей различаются подписью автора, а не разными цветами. Акцентные цвета допустимы для реальных ошибок приложения.

## Повторное тестирование

Перед повтором QA backend проверяет Temporal-цикл, владение задачей в `task_orchestration_owners` и состояния заданий Codex. Он не запускает второго тестировщика при работающем первом и не объявляет завершённый QA ошибкой без доказательств. Если исполнитель завершился, сохранённый результат должен быть прочитан до новой попытки. Устаревшая блокировка снимается только после подтверждения, что процесс завершён либо отсутствует; при недоступности Temporal запуск не разрешается.

Ни готовность QA-плана, ни запуск без выполненных проверок не считаются успешным тестированием. Если есть подтверждённые ошибки кода, задача возвращается разработчику; если недоступны инструменты, тестировщик документирует непроверенные кейсы и запрос на явное согласование.

## Отмена задачи и очистка

Ручная операция отмены недоступна после слияния PR, при активном процессе, существующей зависимости других задач или версии общей проектной документации, привязанной к задаче.

Перед отменой отображаются перечень удаляемых артефактов и **простое подтверждение действия** без ввода текста. Для принадлежавшего задаче PR проверяется GitHub-репозиторий, UUID-ветка, отсутствие merge и отсутствие других PR/зависимостей. GitHub PR закрывается, а ветка удаляется; **удалять сам Pull Request из истории GitHub API не позволяет**.

В PostgreSQL удаляются запись задачи, её переписка, собственный QA-план, принадлежащие ей тест-кейсы/флоу без сторонних ссылок, и документы с явным `created_by_task_id`. Общие тесты и документы не затрагиваются. Факт отмены, пользователь и количество удалённых артефактов остаются в `task_cancellation_audit`. Исключено удаление чужой ветки либо базовой ветки репозитория. Проверки GitHub и SQL не представляют собой распределённую транзакцию; при частичном сбое повтор должен быть безопасен.

## Остаточные ограничения

- Динамическая доступность кнопок — не замена сквозному тестированию реальным Codex и Temporal.
- Браузерное E2E, автоматическое развёртывание изолированного приложения и screenshot/trace-инструменты пока не реализованы.
- Очистка может удалять только **явно атрибутированные** задаче документы. Ранее созданные документы без атрибуции не удаляются автоматически.
- Для активной задачи сначала нужно завершить или отменить её Temporal-процесс; автоматическое прерывание всех внешних исполнителей с последующим удалением требует отдельной полноценной проверки.


## Результаты повторного аудита

При ответе на последний вопрос, вызванный **неопределённостью аналитика**, прежнее заключение для того же SHA и версии ТЗ помечается устаревшим и анализ выполняется заново. Если аналитик уже выявил **существенное изменение поведения**, ответ на сопутствующий вопрос не заменяет отдельного согласования изменения.

Отмена задачи также должна обнаруживать UUID-ветку, которую Codex успел отправить в GitHub до завершения создания PR и записи `git_branch` в задачу. История попыток запуска является основанием проверить и удалить эту ветку.

Восстановление зависшего QA доступно из закреплённой панели действий, даже если экран показывает устаревший признак активного процесса. Backend сначала проверяет Temporal и исполнитель, и только после подтверждения отсутствия другого активного QA допускает новый запуск.

Неподтверждённые документы без `created_by_task_id` **не** удаляются автоматически, поскольку они могут быть общими. Это ограничение раскрывается пользователю до подтверждения удаления. См. [полный аудит требований](CONVERSATION_REQUIREMENTS_AUDIT.md).
