# AI Development Orchestrator

Веб-сервис для совместной разработки проектов людьми и ИИ-агентами.

## Реализовано — локальный MVP

- Авторизация администратора; учётные данные задаются при запуске через переменные окружения.
- Создание проектов, обзор проекта.
- Канбан с перетаскиванием задач между пятью этапами, переключение на список.
- Создание и редактирование задач, тип задачи и выбор родителя, журнал смены этапов.
- Ручная настройка режима этапа: ручной / с подтверждением / автоматический. **Автоматические переходы пока не исполняются** — это настройка будущего оркестратора.
- Раздел документации: дерево вложенных страниц, создание корневых и дочерних страниц, раскрытие веток, изменение родителя, редактор содержимого (пока без истории версий). Существующие страницы при обновлении остаются на корневом уровне.
- Сохранение OpenAI API-ключей и GitHub token с AES-256-GCM. Для GitHub реализована проверка доступа с правом записи и привязка репозитория к проекту. Авторизация Codex через ChatGPT и тестовый запрос доступны; выполнение задач и Git-операции агентом ещё не реализованы.
- Данные проектов, задач, документов и подключений сохраняются в PostgreSQL.

**Локальный администратор:** если в существующем `.env` указан `ADMIN_EMAIL=admin@localhost`, приложение автоматически использует `admin@localhost.test` и при старте переименует существующего пользователя в БД, сохранив его пароль, ID и доступы. Для входа используй **admin@localhost.test**. Менять `.env` необязательно, но можно явно установить `ADMIN_EMAIL=admin@localhost.test`.

## Быстрый запуск

Требуются Docker и Docker Compose.

```bash
cp .env.example .env
# Отредактируйте .env: уникальные сложные пароли и JWT_SECRET;
# CREDENTIALS_KEY — 32 случайных байта в hex (openssl rand -hex 32).
docker compose up --build -d
```

Откройте `http://localhost:8080` и войдите с `ADMIN_EMAIL` и `ADMIN_PASSWORD` из `.env`.

**Безопасность:** версия предназначена для локального или закрытого тестового окружения. **Не публикуйте HTTP-порт напрямую в интернет.** Перед внешним доступом обязательны HTTPS, обратный прокси и дополнительные проверки безопасности. Не используйте реальные рабочие ключи, пока не проверена инфраструктура. `CREDENTIALS_KEY` нужно сохранить для последующего расшифрования сохранённых секретов. Смена `ADMIN_PASSWORD` в `.env` после первой инициализации пока не меняет пароль в базе.

## Режим разработки

```bash
npm install
# Поднимите PostgreSQL, задайте DATABASE_URL, ADMIN_EMAIL,
# ADMIN_PASSWORD, JWT_SECRET и CREDENTIALS_KEY
npm run dev:api
npm run dev:web
```

## Codex CLI через подписку ChatGPT (локальный стенд)

Docker Compose поднимает внутренний сервис `codex` с официальным CLI. Он **не публикует порт наружу**. Данные авторизации Codex хранятся в отдельном томе `codex_auth` (вне БД приложения) и сохраняются при пересоздании контейнера.

1. Обновите проект: `git pull` и `docker compose up --build -d`.
2. В приложении откройте **Настройки аккаунта** в боковом меню → **Codex CLI · ChatGPT Plus**. Настройка не зависит от выбранного проекта. На первой итерации вход доступен администратору и технически использует один общий Docker-том `codex_auth`; персональные хранилища для нескольких пользователей пока не реализованы.
3. Нажмите **Подключить ChatGPT Plus**. В блоке появится адрес сайта и одноразовый код авторизации устройства. Если код не появился сразу, нажмите **Проверить состояние**.
4. Откройте адрес в своём браузере, войдите в ChatGPT и подтвердите одноразовый код. **Пароль ChatGPT, API-ключ, cookie и auth.json в интерфейс не вводятся.**
5. Дождитесь статуса «Подключён», затем нажмите **Проверить запросом**. Этот тест отправляет небольшой запрос через подписку и расходует часть её лимита.

При необходимости сначала включите вход по коду устройства в настройках безопасности ChatGPT. Метод официально описан в [документации Codex](https://learn.chatgpt.com/docs/auth). Если сайт или политика аккаунта не разрешает авторизацию устройства, подключение через Plus таким способом не сработает. API-ключ — отдельный способ оплаты OpenAI API, для этого сценария он не нужен.

**Безопасность:** код устройства показывается только авторизованному администратору. Не публикуйте порт приложения в интернет. Docker-том `codex_auth` содержит токены доступа; не копируйте и не коммитьте его содержимое. Команда `docker compose down -v` удалит и этот том (а также том БД) — не используйте её для обычного обновления.

В **настройках аккаунта** доступны подключение Codex, проверка статуса, тестовый запрос и отключение. В **настройках проекта** доступны модель по умолчанию и ручной запуск задач через Codex в отдельную Git-ветку с созданием draft PR. Полноценная очередь, восстановление после перезапуска и автоматические переходы workflow пока не реализованы.

## Привязка репозитория GitHub к проекту

1. В GitHub откройте **Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**: https://github.com/settings/personal-access-tokens/new
2. Выберите владельца репозитория и доступ **Only select repositories**, указав только нужный репозиторий. Для Repository permissions установите **Contents: Read and write** и **Pull requests: Read and write** (Metadata: Read предоставляется автоматически). Не давайте права на другие репозитории и не используйте токен с полным доступом ко всему аккаунту.
3. В приложении откройте проект → **Настройки** → **Подключения** → **Добавить подключение**. Заполните **Название** (например, `GitHub — основной` — это только подпись для удобства), **Тип** = `GitHub token`, **Секрет** = значение токена `github_pat_...`, скопированное из GitHub. В форме есть встроенная пошаговая инструкция. Токен хранится в БД зашифрованным, не отображается при просмотре. Никогда не публикуйте его в чате, репозитории или логах.
4. В блоке **GitHub · Репозиторий проекта** укажите `owner/repository`, выберите созданный токен и нажмите **Проверить и сохранить**. Сервис проверяет репозиторий через GitHub API и право записи, фиксирует его стандартную ветку. Можно изменить токен/репозиторий или отвязать связь.
5. В **Настройках проекта → AI · Настройки выполнения** выберите модель и глубину рассуждений, установите ограничение времени и включите **Разрешить ручной запуск AI-задач**. По умолчанию функция **выключена**, модель — `gpt-6-luna`, глубина — `low`. Разработка имеет технический таймаут 30 минут.
6. Откройте задачу и нажмите **Запустить Codex → Pull Request**. Исполнитель клонирует связанную ветку репозитория в отдельную временную папку, запускает Codex в режиме workspace-write, создаёт новую ветку `ai/task-...`, фиксирует изменения, отправляет ветку и открывает **draft Pull Request**. Основная ветка не изменяется. Статус отображается в задаче и настройках проекта.
7. Для первой версии поддерживается один одновременный запуск на исполнитель (даже для разных проектов), только ручной старт администратором. Авторизованный Codex CLI должен иметь доступ к выбранной модели; доступность зависит от аккаунта и версии CLI.
8. После старта **не перезапускайте контейнер codex до завершения задачи**: MVP хранит состояние выполняющегося процесса в памяти контейнера; результат фиксируется в БД при опросе статуса. При перезапуске работа прервётся.
9. Текущие ограничения: нет автоматического запуска по перемещению карточки, нет одобрения/слияния PR внутри сервиса, нет автоматического исполнения тестов, нет точного учёта токенов. Низкая глубина, бюджет времени и ручной запуск уменьшают риск расхода, но не гарантируют лимит токенов. Проверяйте PR вручную перед слиянием.

Для локальной эксплуатации не раскрывайте доступ к веб-сервису за пределы доверенной сети. При отзыве токена в GitHub проверку подключения нужно повторить с новым токеном. **Если токен создавался только с Contents: Read and write, выдайте ему также Pull requests: Read and write** (либо создайте новый Fine-grained token и замените подключение).

## Документация и правила проекта — раздельные механизмы

**Документация** отражает реализованную функциональность, а не намерения. После успешного GitHub merge задача переходит в отдельную колонку **«Документация»**. Там задачи накапливаются. Кнопка **«Обновить документацию»** над колонкой запускает один AI-запрос по группе до 15 слитых задач. AI обновляет специальную страницу **«Реализованные возможности»**, не перезаписывая остальные страницы, сохраняет новую версию и только после успешного обновления переводит задачи в **«Готово»**. Если AI не ответил, задачи остаются в очереди. Версии хранятся отдельно в Postgres.

**Правила проекта** доступны в отдельной вкладке проекта как самостоятельный список, не смешанный с документацией. Пользователь может добавлять и удалять правила. Утверждённые правила включаются в контекст постановки задач, AI-анализа, обсуждений, Codex-разработки и обновления документации. Во время анализа AI может предложить новые универсальные правила; они отображаются отдельно со статусом **«Принять» / «Отклонить»**, без самостоятельного изменения обязательных инструкций.

**Ограничения MVP:** пакет обрабатывает максимум 15 задач за запуск; обновление выполняется по описаниям и ссылкам на слитые PR, без отдельного анализа diff. AI-документ может требовать ручной проверки, особенно если текст задачи не совпадает с фактическими изменениями. Пока история версий хранится в БД, но не имеет интерфейса восстановления. Полное автоматическое поддержание тематических страниц отложено: чтобы не перезаписывать материалы людей, обновляется только AI-управляемая страница.

## Согласованный первый workflow — анализ → разработка → очередь PR → слияние

1. Пользователь просит в общем чате **«Создай задачу …»**. Codex формирует начальное ТЗ с учётом описания проекта, недавней документации и других задач. Новая карточка **сразу попадает в «Анализ»**, а блокирующие вопросы и предложения о связях записываются в чат этой задачи. Дубликаты не удаляются автоматически.
2. В карточке справа пользователь отвечает на вопросы. В режиме анализа каждое сообщение AI повторно уточняет ТЗ в левой части, обновляет открытые вопросы и потенциальные связи. Когда вопросов нет, становится доступной **«Отправить в разработку»**.
3. Нажатие подтверждения сохраняет требования, переводит карточку в **«Разработку»** и **автоматически запускает Codex**. Если исполнитель занят, GitHub не подключён, достигнут лимит или есть связанные задачи в разработке/очереди PR, запуск отклоняется с сообщением; карточка остаётся в разработке для повторного запуска кнопкой «Выполнить».
4. Исполнитель клонирует репозиторий, создаёт индивидуальную ветку, вносит изменения, делает commit/push и создаёт обычный PR к **целевой ветке проекта** (`target_branch`). После успешного PR и следующего опроса состояния карточка попадает в **«Ожидает слияния»**. Ветка и URL PR сохраняются в карточке.
5. В колонке **«Ожидает слияния»** есть кнопка **«Слить готовые»**, а в карточке — **«Слить»**. Система проверяет состояние PR, конфликтность, результаты доступных GitHub Check Runs и актуальный SHA и просит GitHub произвести merge; GitHub продолжает применять собственные branch protection. Групповое действие идёт **последовательно**, сообщает число слитых и пропущенных PR. После подтверждения GitHub карточка переходит в «Документация», и только после обновления документов — в «Готово».
6. Обычное изменение этапа или перетаскивание карточки не может напрямую выставить «Разработка», «Ожидает слияния» либо «Готово». Статусы подтверждаются соответствующими операциями workflow.

**Настройка GitHub:** в параметрах проекта выбери целевую ветку PR (по умолчанию текущая основная, обычно `main`; `master` допускается только если такая ветка существует). Токену нужны `Contents: Read and write`, `Pull requests: Read and write` и `Checks: Read`. Если ранее указал только Contents, обнови права токена и сохранение подключения. Слияние происходит исключительно по явной команде пользователя.

**Ограничения текущего MVP:** связанные задачи **помечаются**, но не объединяются автоматически, и зависимости пока не образуют полноценный граф. Автоматический анализ использует ограниченный контекст задач и документов, а не весь код. Полноценная очередь, устойчивое восстановление после перезапуска, результаты CI в интерфейсе, комментарии к diff и интеллектуальное группирование в общую ветку остаются следующими этапами. **Сквозное выполнение в локальном Docker требует отдельной проверки**; изменения в GitHub не подтверждают его успешность.

## Реальные лимиты Codex в аккаунте ChatGPT

**Настройки аккаунта → Лимиты Codex · ChatGPT** показывают доступные окна лимитов для авторизованного Codex CLI. Данные получаются из официального Codex app-server через метод `account/rateLimits/read`. Для каждого доступного окна выводятся оставшийся процент, длительность окна и время следующего сброса; значения считываются по запросу или при открытии настроек. Если лимиты не предоставляются, интерфейс сообщает об этом, не подставляя вымышленные цифры.

Это именно **лимиты Codex, предоставленные аккаунту ChatGPT**, а не универсальный остаток сообщений обычного ChatGPT и не локальные ограничения нашего сервиса. Ранее добавленные собственные дневные лимиты на чаты и количество запусков **удалены** из механизма исполнения. Оставлен только фиксированный технический таймаут процесса разработки (30 минут), защищающий от зависаний.

**Навигация:** правила — отдельная вкладка; документация после слияния обновляется из колонки канбана, без отдельной панели в настройках; история AI-запусков отображается в карточках задач; GitHub-токен и привязка репозитория управляются из одного блока настройки проекта.

## Карточка задачи, общение с AI и подключение пустого GitHub-репозитория

- **Enter отправляет сообщение** в общем чате проекта и в чате задачи; **Shift+Enter** вставляет новую строку.
- В карточке название и техническое задание по умолчанию выводятся обычным текстом. На hover справа появляется карандаш; его нажатие открывает редактирование. Изменения в полях сохраняются автоматически при выходе из режима редактирования (без отдельной кнопки «Сохранить»). Изменения ТЗ, предложенные AI после ответов, сохраняются сразу на сервере.
- **Контекст AI**: утверждённые правила, описание проекта, до 10 последних страниц документации, недавние задачи и теперь **подключённый репозиторий + целевая ветка из настроек**. При обсуждении задачи дополнительно используются её описание, история переписки, открытые вопросы и другие задачи. AI должен собрать все блокирующие вопросы сразу, а не по одному; уже настроенный репозиторий или GitHub Pages без явной просьбы пользователя не являются вопросами.
- Верх карточки содержит действия текущего этапа: «Отправить в разработку», «Запустить разработку» (если нужен повторный запуск), «Слить PR», «Обновить документацию». Отдельный блок «Исполнение» удалён. В правой части одной хронологией идут переписка, история действий, статусы запусков Codex, ошибки и ссылки на PR.
- **Нижняя шкала** показывает этапы, выполненные и текущий. Стрелки переходов активируются, когда соблюдены условия workflow; анализ → разработка подтверждает ТЗ и запускает Codex, а разработка → ожидание слияния определяется созданием PR, не ручным перемещением статуса.
- **Пустой GitHub-репозиторий при подключении**: если у него вообще нет веток, оркестратор создаёт первый коммит с README.md в его default-ветке, после чего привязывает существующую целевую ветку. Для репозиториев, где коммиты уже есть, начальные файлы не создаются. Выбранная пользователем другая целевая ветка должна реально существовать. Перед каждым запуском разработки целевая ветка повторно проверяется, ошибка GitHub возвращается до расходования запуска Codex.
- На первом этапе прогресс Codex показывается при опросе статуса запуска в карточке; после перезапуска контейнера активный процесс не восстанавливается. Реальное поведение чатов и автоматического редактирования нужно проверить на локальном Docker.

## Диагностика разработки и отступы интерфейса

При запуске Codex получает рабочую копию GitHub-репозитория, привязанные правила и утверждённое описание задачи. Агенту явно задано **создавать исходные файлы, если проект пока содержит только README**, а не ограничиваться текстовым ответом. Если первый запуск прошёл без файловых изменений, исполнитель выполняет одну повторную попытку с усиленным требованием. Если изменений вновь нет, в истории задачи показываются последние текстовые ответы Codex и диагностические сообщения (без GitHub-токена), чтобы различить отказ модели, отсутствие инструментов и проблемы песочницы. Это не заменяет сквозной тест в пользовательском окружении.

Веб-интерфейс использует единые вертикальные и горизонтальные промежутки между разделами (основная сетка 24 px, уменьшенная для узких экранов). Это касается настроек, правил, документации, Kanban и окна задачи.

## Параллельные AI-процессы и состояние разработки

- Окно задачи блокирует **прокрутку страницы под модальным окном** до его закрытия, не мешая прокрутке переписки и описания внутри.
- AI-диалоги **не ждут завершения разработки**: запросы нового проекта/задачи могут работать одновременно с активными Git-агентами. В первой локальной версии допускается до **4 одновременно выполняемых AI-диалогов**; дополнительные запросы получают понятное сообщение о загрузке, а не блокируются фактом разработки.
- Разработчики работают в изолированных временных копиях GitHub-репозиториев: **до 3 одновременных процессов Codex**, остальные задания получают статус **«В очереди»** и стартуют по мере освобождения слота. Это техническая защита локальных ресурсов, а не лимит использования подписки. Блокировка повторного запуска действует только на **ту же задачу**, не на весь проект.
- В карточке отображаются текущий этап, очередь и прошедшее время. Состояния Codex записываются в историю задачи; после перехода из очереди в работу статус обновляется.
- Ограничение времени **применяется ко всему запуску, включая повторную попытку**, а не заново для каждой попытки. Текущая техническая защита — 30 минут суммарно. Остановка не считается успешной разработкой и не создаёт фиктивный PR.
- Очередь и активные процессы пока находятся **в памяти контейнера**. Перезапуск во время выполнения прервёт задания; для устойчивого продолжения после рестартов нужен отдельный исполнитель и постоянная очередь. Максимальный параллелизм может упираться в ограничения аккаунта Codex и ресурсы машины — успешность реальных параллельных запусков нужно проверить в Docker.

## Ветка задачи, параллелизм и исправление Sandbox Codex

- **Имя ветки = полный UUID задачи**, без префикса и суффикса запуска, например `123e4567-e89b-12d3-a456-426614174000`. Этот ID отображается прямо в заголовке карточки в Kanban и вверху окна задачи.
- В первой версии **одна задача имеет одну постоянную ветку**: после клонирования исполнитель сразу публикует ветку в GitHub (даже до начала изменений Codex), привязывает её к задаче, а при повторном запуске проверяет наличие ветки и продолжает в ней. При наличии существующего открытого PR к нужной базе оркестратор обновляет существующую ветку и не создаёт дубликат PR. В будущем задача может иметь несколько независимых веток, но **в одной ветке одновременно работает не более одного агента**.
- Исполнитель держит блокировку по `repository + task_id`; другие задачи могут исполняться параллельно в своих временных копиях.
- **Исправление ошибки записи:** стандартный внутренний sandbox Codex (`workspace-write`) на Linux требует возможностей пространства имён, которые текущий Docker-контейнер блокирует. Для разработки Codex запускается в `codex exec --sandbox danger-full-access` (неинтерактивный запуск; флаг `--ask-for-approval` у `codex exec` не поддерживается) **внутри отдельного Docker-контейнера**: контейнер, а не вложенный sandbox, становится границей безопасности. Контейнер работает под пользователем `node`, без Docker socket, с отброшенными Linux capabilities и `no-new-privileges`. GitHub-токен и секрет авторизации внутреннего API не передаются процессу Codex; Git-операции выполняет исполнитель. **Не подключайте к такому контейнеру хостовые директории с секретами, кроме необходимого авторизационного тома Codex.** Учётные данные Codex остаются доступными внутри самого контейнера, поэтому режим пока предназначен для доверенных репозиториев и локального MVP.
- Инструкция агенту запрещает использовать GitHub MCP для изменения файлов. Codex меняет локальную копию, после чего Git worker проверяет изменённые файлы, выполняет commit и push и создаёт/обновляет PR.

**Проверка:** сборка GitHub Actions проверяет типы веб/серверного кода и синтаксис worker, но не проверяет реальную Linux-изоляцию и запись через Codex. После обновления нужно повторить тест с созданием `index.html`, убедиться, что появился коммит в ветке UUID и PR. Неудача должна показывать фактическую диагностику, а не выдавать фиктивный успех.

## Autoscroll, фактические токены и восстановление PR

- В общем чате и в карточке задачи при поступлении новых сообщений UI автоматически прокручивает ленту к последнему. Для карточки это включает также историю событий и обновления статуса запуска Codex.
- Теперь `codex exec --json` отдаёт события `turn.completed` с `usage.input_tokens`, `usage.cached_input_tokens` и `usage.output_tokens`. Исполнитель читает эти данные для новых AI-диалогов и разработок, включая повторные попытки, и записывает в Postgres `ai_token_usage`. Разработка учитывается по уникальному ID запуска, исключая повторное сохранение при polling. В **Настройках аккаунта → Использованные токены Codex** показывается суммарный расход с момента включения функции. Это статистика Codex, не показатель денежной стоимости и не история до обновления. Статистика доступна, если CLI действительно выдаёт usage в JSON. При аварийном завершении до события `turn.completed` расход может быть неполным.
- Ошибка `GitHub HTTP 403` при проверке существующего PR не означает, что файлы не созданы: коммит и push могут уже завершиться. Отдельной кнопки восстановления нет: обычное действие **«Запустить разработку»** прежде всего проверяет, есть ли уже закоммиченные изменения в постоянной ветке задачи. Если изменения есть, сервис автоматически создаёт/находит PR, обновляет колонку и **не вызывает Codex повторно**. Если изменений нет, запускается стандартная разработка. Если GitHub не разрешает читать/создавать PR, требуется токен с **Pull requests: Read and write** на этот репозиторий. Эти права также проверяются при сохранении GitHub-подключения в настройках проекта. AI не может обойти отсутствие разрешений токена. Для новых запусков проверка доступа к PR выполняется до запуска Codex, чтобы не расходовать лимиты бессмысленно.

## Создание задачи текстом из Kanban

Рядом с кнопкой **«Создать задачу»** находится отдельная квадратная синяя кнопка с пиктограммой документа. Она открывает общий AI-чат проекта, подставляет начало команды **«Создай задачу: »** и ставит курсор в поле ввода. Уже набранный текст не перезаписывается. После отправки используется существующий AI-анализ и создание задачи; отдельный конкурирующий механизм постановки задач не добавляется.

## Зависимая разработка и Stacked Pull Requests

- У задачи есть отдельное поле **«Зависит от задачи»**. AI автоматически определяет *кодовую зависимость* в ходе постановки и анализа, отличая её от обычной смысловой связи. Пользователь может вручную выбрать родителя или снять зависимость; ручное решение имеет приоритет. API не позволяет создать циклическую зависимость или ссылку на задачу другого проекта.
- **Задача B зависит от A:** если A находится в «Ожидает слияния» с опубликованной UUID-веткой и PR, Codex клонирует **ветку A**, создаёт собственную UUID-ветку B и формирует **PR B → A**. Это позволяет писать код B, используя ещё не слитые изменения A. Другие информационно связанные задачи не блокируют разработку.
- Если A уже слита (этап «Документация» или «Готово»), B стартует от настроенной целевой ветки проекта. Если A ещё анализируется или разрабатывается без готового PR, B пока ждёт публикации результата A; пользователь получает точное объяснение. Два агента не могут работать в одной ветке одновременно.
- После merge A через **merge commit** сервис проверяет, что коммит A входит в новую базовую ветку, и меняет базу открытого PR B на ветку, в которую слита A. При отсутствии подтверждённого общего предка PR B **не перестраивается вслепую**: ошибка фиксируется в событиях задачи и её надо устранить до слияния. При попытке слияния B проверка и безопасное переключение повторяются. Для корректного изменения PR при squash/rebase потребуется отдельный механизм restack.
- При групповом слиянии PR сортируются по глубине зависимостей, сначала родители. Слияние дочернего PR до родительского не допускается. Слияние всё равно требует явной команды пользователя.
- У каждой задачи собственная ветка, называемая её **полным UUID**. Сейчас поддерживается одна непосредственная кодовая зависимость (цепочки возможны); множественные родители и автоматическое разрешение конфликтов отложены.

**Проверка:** создавать A и B в одном тестовом репозитории, дождаться PR A, связать B с A, отправить B в разработку, проверить, что base PR B равен UUID ветки A; слить A и проверить автоматическое изменение base PR B на `main`. Сквозной сценарий с реальным GitHub пока требует подтверждения в локальном Docker.

## Ошибки, компактный AI-чат и генерация документации

- Ошибки API/интерфейса выводятся всплывающим уведомлением **поверх контента справа снизу**, включая экран входа и открытые диалоги. Уведомление закрывается по крестику либо автоматически примерно через 9,5 секунды.
- У проектного чата кнопка отправки стала компактной квадратной и содержит только иконку самолётика. Поле ввода занимает оставшуюся ширину.
- Команды **«Создай документ об архитектуре»**, **«Создай документацию проекта»**, **«Добавь страницу про развёртывание»** и другие явные запросы на документ обрабатываются Codex как создание полноценной Markdown-страницы в разделе документации.
- По ссылке на папку Markdown в GitHub AI теперь может **прочитать исходные файлы, синтезировать новый тематический комплект из 3–6 документов** и сохранить его в разделе «Документация» текущего проекта как вложенные страницы. Исходный репозиторий не изменяется. Это не побайтовый импорт: структура и тексты пересобираются по смыслу с сохранением фактов и указанием источников. Существующие автоматически созданные документы не перезаписываются.
- При неоднозначном запросе помощник **уточняет действие либо предлагает 2–3 варианта**. Для GitHub-переноса при отсутствии ссылки спрашивает источник и разницу между переработкой и копированием, а не выдумывает отсутствие сессии документов или других интеграций. Он получает правила проекта, описание и существующие разделы, может выбрать существующую родительскую страницу.
- После сохранения AI возвращает в чат подтверждение с действием **«Открыть документ»**; оно выбирает страницу на вкладке «Документация». Ссылку сохраняем в истории диалога.
- Команда про **создание задачи**, в которой упоминается документация, не должна ошибочно создавать документ. Простое обсуждение без явной команды создания также не изменяет документы.
- Это автономное создание документа по запросу из проектного чата, а не обновление всех документов по итогам слияния PR.

## Навигация по URL и прямые ссылки

Приложение использует HTML5 History API и полноценные адреса для навигации. Левое меню, карточки проектов, карточки Kanban, табличный список задач, дерево документации и хлебные крошки используют настоящие ссылки (поддерживается Ctrl/Cmd+click и открытие в новой вкладке).

| Экран | Путь |
| --- | --- |
| Все проекты | `/projects` |
| Настройки аккаунта | `/account/settings` |
| Обзор проекта | `/projects/{projectId}/overview` |
| Канбан / список задач | `/projects/{projectId}/tasks` |
| Конкретная задача | `/projects/{projectId}/tasks/{taskId}` |
| Документация | `/projects/{projectId}/docs` |
| Выбранный документ | `/projects/{projectId}/docs/{docId}` |
| Правила проекта | `/projects/{projectId}/rules` |
| Настройки проекта | `/projects/{projectId}/settings` |

Прямой переход и обновление страницы восстанавливают выбранные проект, вкладку, задачу или документ после загрузки данных через API. При отсутствии сессии сначала открывается форма входа, затем экран по первоначальному URL. Переходы внутри приложения записываются в историю браузера; работают «Назад» и «Вперёд». Неизвестные и недоступные пути возвращают на список проектов с уведомлением, а не показывают пустой экран.

`apps/web/nginx.conf` уже настроен на `try_files $uri $uri/ /index.html`, поэтому глубокие ссылки открываются также при перезагрузке и при вставке адреса в новую вкладку. URL относятся только к отображению: доступ к данным по-прежнему проверяет API и авторизация.

**Проверка:** открой задачу и документ, скопируй адрес, обнови страницу и открой в другой вкладке. Попробуй «Назад/Вперёд», а затем Ctrl+click по странице дерева документации и по карточке задачи. Проверить это в пользовательском браузере из GitHub Actions нельзя, там выполняются проверки сборки/типов.

## Пакетное слияние и GitHub CI

При **«Слить готовые»** оркестратор обрабатывает PR по порядку зависимостей и перед слиянием проверяет их готовность, Check Runs и статусы коммитов. Если подключённый Fine-grained GitHub token получает HTTP 403 на чтении Check Runs/статусов, приложение пробует получить те же данные через публичный read-only GitHub API **без токена**. Это подходит только публичным репозиториям, в которых данные проверок доступны для анонимного чтения. Проверки не пропускаются: при недоступности обеих попыток слияние блокируется с инструкцией выдать токену `Checks: Read` и `Commit statuses: Read` для данного репозитория. GitHub также самостоятельно применяет branch protection при фактическом merge.

Для закрытых репозиториев следует сразу выдать Fine-grained token `Contents: Read and write`, `Pull requests: Read and write`, `Checks: Read` и `Commit statuses: Read`. Пакетный отчёт отображает итоговые числа, а уникальные сообщения ошибок — во всплывающем уведомлении справа снизу. Успешно слитая задача переходит в «Документация», а не непосредственно в «Готово».

## Проверка первого workflow в локальном Docker

1. Обновить контейнеры, проверить Codex CLI в настройках аккаунта; включить ручной AI в настройках проекта.
2. В GitHub-подключении убедиться, что выбрана существующая целевая ветка (обычно `main`) и токен имеет Contents: Read/write, Pull requests: Read/write, Checks: Read.
3. В мини-чате написать «Создай задачу на …». Новая задача должна сразу появиться в **«Анализе»**, а вопросы — в её чате.
4. Ответить на вопросы справа. AI должен обновить краткое ТЗ слева и снять блокирующие вопросы. Нажать **«Отправить в разработку»**; Codex запустится без второй кнопки.
5. После создания PR задача автоматически попадёт в колонку **«Ожидает слияния»** при опросе статуса. Проверить ветку и изменения в GitHub, нажать **«Слить»** в задаче либо **«Слить готовые»** над колонкой.
6. Проверь, что GitHub подтвердил merge, а задача оказалась в **«Готово»**. Если проверки или конфликты мешают, задача должна остаться в очереди и показать причину.

**Проверка сборки и реальной интеграции с Codex/репозиторием обязательна.** Само наличие коммитов не доказывает успешный сквозной запуск.

## Temporal и первоначальное тестирование (новые запуски)

Новые запуски разработки управляются **Temporal TypeScript Worker**: API запускает workflow, Worker обращается к прежнему Codex CLI (через внутренний контейнер `codex`) и сохраняет историю выполнения. **Авторизация Codex по подписке ChatGPT не менялась; OpenAI API не требуется.**

Пайплайн: `Анализ → Разработка → Тестирование → Ожидает слияния → Документация → Готово`. После создания PR отдельный AI-тестировщик анализирует изменения в собственной временной копии ветки и запускает доступные локальные тесты. При обнаружении дефектов агент возвращает задачу в «Разработку» с отчётом и запускает исправление в прежней ветке; максимум три автоматических цикла исправления. После успешной проверки PR отправляется в «Ожидает слияния». Если нет достаточного тестового окружения, вердикт — «Проверка заблокирована», без ложного статуса успеха. Для задачи в «Тестировании» предусмотрен ручной повтор проверки.

`docker compose up -d --build` теперь запускает `temporal` и `temporal-worker`. Образ `temporalio/temporal:1.10.0` запускает **встроенный dev-сервер Temporal** с SQLite на постоянном Docker-томе `temporal_data`. **Это конфигурация для локального MVP, не промышленный кластер Temporal**. Temporal Web UI слушает внутри сети Compose на `temporal:8233` и по умолчанию не публикуется на хост. При необходимости его можно вывести **только на localhost**, добавив порт `127.0.0.1:8233:8233` в сервис `temporal`.

История новых workflow хранится в Temporal; результаты тестирования и замечания — также в PostgreSQL и Центре процессов. Очередь Codex пока остаётся внутри контейнера исполнителя: если сам контейнер Codex перезапускается во время команды, активная команда не восстанавливается автоматически. Temporal сохраняет историю и позволяет зафиксировать ошибку, но повторное исполнение произвольного внешнего эффекта без защиты от дубликатов не гарантируется.

**Границы этапа внедрения:** существующие запуски и импорт Markdown пока не переведены на Temporal; для импорта продолжает действовать прежний механизм контрольных точек. Тестирование без отдельной среды не гарантирует проверку UI, интеграций или браузерного поведения. Для настоящего CI/E2E в будущем понадобится конфигурируемый изолированный Test Runner. Не предоставляйте контейнеру Codex доступ к Docker socket или production-секретам.
